# 本地存储与文件目录设计

## 1. 设计目标

系统要支持一个老师长期存放大量学生资料。一个学生可能几十 GB，所以不能把原始文件塞进数据库。

本地存储目标：

- 数据默认只保存在用户电脑本地。
- 原始附件以文件形式保存。
- SQLite 只保存结构化元数据和路径。
- 索引数据单独存放，便于重建和清理。
- 后续可以迁移到团队共享目录或私有云。

## 2. 推荐数据根目录

默认数据目录建议放在系统应用数据目录中，也允许用户在设置里自定义。

Windows 推荐：

```text
C:\Users\<User>\AppData\Roaming\OmniEduAgent\
```

用户也可以选择大容量硬盘，例如：

```text
D:\OmniEduData\
```

## 4. 文件存储原则

### 原始文件

原始文件包括：

- 图片
- PDF
- Word
- 试卷扫描件
- 作业照片
- 音频
- 视频

处理原则：

- 复制到学生目录下，避免源文件被移动后丢失。
- 保留原始文件名。
- 如果文件名冲突，加时间戳或短 ID。
- 数据库记录绝对路径或相对数据根目录路径。

### 文本记录

老师手动输入的内容可以同时存在两处：

- SQLite 的 `learning_records.content`
- 学生目录下的 `content.md`

MVP 阶段可以只存 SQLite，后续为了可迁移和可备份，可以同步生成 Markdown。

### 缩略图和缓存

图片缩略图、OCR 中间图、临时文件放 `cache/`。

缓存可以删除，不影响核心数据。

## 5. SQLite 与文件系统分工

SQLite 存：

- 学生基础信息
- 学习记录元数据
- 附件路径
- 标签
- 摘要
- 复盘报告正文

文件系统存：

- 原始附件
- 大体积资料
- 导出的报告
- OCR 中间产物
- 向量索引文件

## 6. 检索设计

第一阶段推荐两层检索：

### 关键词检索

使用 SQLite FTS 或普通 LIKE 查询。

可检索：

- 学生姓名
- 学习记录标题
- 内容
- 标签
- 摘要

### 向量检索

后续使用 ChromaDB 或 LanceDB。

可检索：

- 某学生最近常见问题
- 与某个错题相似的历史记录
- 阶段复盘上下文

## 7. 大文件策略

为支持几十 GB 资料：

- 导入文件时显示文件大小。
- 不读取完整大文件到内存。
- 对 PDF/Word 解析采用异步任务。
- 向量化只针对抽取出的文本摘要或片段。
- 支持“仅引用原路径”和“复制到资料库”两种模式。

第一版建议默认复制文件，后续增加引用模式。

## 8. 备份策略

第一版至少预留“导出数据目录”的能力。

后续备份方案：

- 手动备份整个 `OmniEduData` 目录。
- 定时复制 `app.db` 和学生目录。
- 导出单个学生档案。
- 导出阶段报告。

## 9. 安全注意事项

- 不把 API Key 存在 `settings.json` 明文中。
- 不自动上传学生资料。
- AI 调用前展示脱敏文本。
- 日志不记录原始学生资料全文。
- 删除学生时先进入归档，避免误删。
