- 新 JS 工具依赖需要实际 Electron-main 验证。本轮 12/12 宿主通过，不能扩张为正式 IPC/UI 或 installer 通过。

- 只在 failed 状态检查重试次数会留下中途退出绕过预算的窗口：第二次重试已开始后启动恢复原本会把 running 改成 blocked，再次提供入口。启动恢复现读取重试审计并直接标为次数耗尽；专项覆盖该状态迁移。

### 2026-08-11 E07/E08 复盘

- 研究和可视化若只依赖 sidecar capability manifest，主应用仍会把它们当普通问答；必须同时补齐 router 子意图、context policy、tool descriptor、执行分支和可运行 smoke。

- 本地 deterministic evidence 只能证明宿主切片，不等同于联网研究、引用正确性、图表渲染或真实 provider 生产质量。

### 2026-08-11 C05 高级 block 复盘

- 不能为了“支持 interactive/animation”直接把 HTML、iframe 或 SVG payload 注入 Markdown；安全边界应先落在编译器，默认显示占位并要求受控查看器与教师复核。
- `code` block 即使在 fenced code 中也可能被后续消费端误解释，因此本轮对代码文本同样做 scheme/HTML 清理，并明确“只读、不执行”。
- 新 block 类型必须同时更新共享类型、编译器、专项 adversarial smoke 和连续稳定性证据；只改 union 而没有运行时覆盖会造成假支持。

### 2026-08-11 E15 复习 scheduler 复盘

- 直接把 scheduler 逻辑塞进 `mastery-policy.ts` 会让 review queue 无法独立回放；应先抽成纯函数，再由 policy 和 HostTool 共用，保证同一证据不会因入口不同产生不同 due 结果。
- 第一版 smoke 把“首次正确”的 interval 误当成类型序列第一个元素，导致 concept/design 的到期边界断言错误；测试必须明确“初始 state”与“第一次结果后的 state”两个语义。
- timezone 不应参与 epoch due 计算，否则切换地区会移动或丢任务；本轮将 timezone 限定为 bounded 展示元数据，并用三个时区做等值回放。
- HostTool 对超限参数、缺学生和错误 route 都必须在执行前 fail-closed；只测纯函数不能证明真实宿主权限边界。
- recovery smoke 发现 `title` fallback 会把普通备注变成新知识点并改变排序；修复为只接受显式 `metadata.knowledgePoint` 或受控 mastery 标签，并增加重启后 unknown note 不改变 queue 的回归断言。
- Electron smoke 进一步发现 quiz grade 的通用 concept 默认值会重分类 procedure 点；写回前必须从同一 snapshot 读取显式 `knowledgeType`，否则后续 `mastery_assess` 会错误放行。
- 提醒不应通过新增“已提醒/待提醒”业务表制造第二份状态；应用启动和学生切换时重算摘要即可。纯函数必须显式丢弃负数、NaN、重复和超长候选，并把“展示时区”与 epoch due 解耦。
- 高负载验收要同时测 native SQLite 纯读和真实 Electron IPC；前者 pass^3 不能替代后者。当前 8×200、16 并发的两层证据都远低于 2 秒，后续仍需在目标发布硬件上复测。

### 2026-08-11 E10/E12 待作答题恢复复盘

- 只有内存里保留“当前题目”会在重启或模型再次询问时丢失 Mastery 交互状态；恢复入口必须直接查询 `ai_mastery_questions`，并让 `mastery_status` 与 `mastery_grade` 共用这条 SQLite 真源。
- 为了兼容“回答当前题目”的自然语言调用，`questionId` 可以省略，但回退范围必须绑定已解析学生；跨学生校验要放在 `status` 判断之前，否则另一学生的题目可能先以 `already_graded` 等错误掩盖越权原因。
- 对外题目投影必须白名单字段；`expectedAnswer` 和已提交答案即使数据库存在，也不能进入 renderer、checkpoint 或 sidecar event。重启、无题号评分和跨学生攻击必须成为固定回归用例，而不是只测 happy path。
- 多题 quiz 不能只在 renderer 里维护数组，否则 close/reopen 会丢失进度；本轮用 SQLite 事务写入最多 5 行，公开只展示第一题，后续由 oldest-first pending 查询驱动。重复建组必须阻断，避免两个 AgentLoop 同时争抢“当前题目”。
- 仅按 oldest-first 读取还不够，评分入口也必须检查 queue head；否则模型携带后续 `questionId` 仍可跳过前置题。现在 main 在写回前返回 `question_order_mismatch`，并有异常 answered 状态回归。

### 2026-08-11 R13 附件探索复盘

- 不能把“有附件”直接等同于把附件全文注入 Agent context；DeepTutor 的关键是 manifest + 按需 `read_source`。本轮将探索工具限定到学生记录中的 attachment handle，并且只返回脱敏 OCR 片段。

- source scope 必须在主进程再次校验，不能相信模型传入的 attachmentId；不属于当前记录的 ID、无学生、无 OCR 文本都要 fail-closed，不能回显本地路径作为错误提示。

#### 问题 3：思考过程默认折叠会被认为没有暴露

发生了什么：

- `ChainOfThought` 放在 AI 回复内，但结果出来后默认折叠，用户无法直接看到。

为什么错：

- 用户的交互目标是“回复中能看到思考过程”，不是需要再手动展开才发现。

下次如何改：

- 在 AI 回复内默认展开可验证的“思考过程摘要”。
- 展示任务识别、上下文读取、证据边界、知识来源、产物判断等外部过程。
- 不展示或编造模型内部隐式推理。

#### 问题 4：普通浏览器 dev URL 不能验收 Electron IPC 持久化

发生了什么：

- 用 Chromium 打开 `localhost` 验收 AI 对话保存时，点击 Send 没有创建 SQLite session。
- 原因不是数据库链路本身，而是普通浏览器没有 Electron preload，`window.omniEdu` 不存在。

为什么错：

- AI 对话持久化依赖 preload 暴露的 IPC API；脱离 Electron 窗口测试只能验证纯 renderer UI，不能验证本地数据库。
- 如果把普通浏览器结果当作最终验收，会误判功能未实现或漏掉 IPC 问题。

下次如何改：

- 涉及 SQLite、文件系统、preload、main IPC 的功能必须用 Electron + Playwright 或正式 smoke 脚本验收。
- 浏览器 dev URL 只用于检查布局、样式、Vite overlay 和纯前端交互。

#### 问题 5：HeroUI Pro 组件事件需要和项目提交入口做适配

发生了什么：

- `PromptInput` 根组件传了 `onSubmit`，但 Send 点击路径在当前嵌套结构中没有稳定进入业务提交。
- 补充 `PromptInput.Send` 的显式 click 处理后，UI 发送可以创建本地会话和消息。

为什么错：

- 直接复用本地 HeroUI Pro 源码不等于调用处无需适配；项目侧仍要验证键盘、按钮、禁用态和重复提交。

下次如何改：

- 对输入类组件同时验收 Enter 和按钮点击。
- 用提交锁避免按钮 click 与组件 onSubmit 双路径导致重复保存。

#### 问题 6：思考过程和工具调用不能固定铺满

发生了什么：

- AI 控制台曾对所有回复固定展示学生档案、学习记录、附件、知识库和知识图谱。
- 用户问“你好”时也看到一堆不相关上下文，体验像假流程。

为什么错：

- 思考过程摘要应该是可验证的外部处理过程，不是装饰性流程清单。
- 工具调用和上下文来源必须来自本轮真实需要或真实命中；否则会误导老师以为系统读取了无关数据。

下次如何改：

- 先按 prompt 和实际结果生成 trace，再把 `thoughtSteps`、`contextSources`、`toolRuns` 存入 message metadata。
- 渲染时只读当前消息 metadata；没有来源或工具时不显示 `ChatSources` / `ChatToolGroup`。
- 问候、闲聊、设置类输入要明确“不调用本地学生上下文”。

#### 问题 7：AI 文档产物入口不能只做附件卡片

发生了什么：

- 产物入口曾用 `ChatAttachment` 卡片显示，用户要求回复中显示“XXX 文件”文字，点击文字后右侧展开文件。

为什么错：

- 用户期望的交互是 ChatGPT / Codex 风格的文内产物链接，而不是额外附件区块。
- 如果产物入口不写入消息 metadata，历史对话打开后入口会丢失。

下次如何改：

- AI 回复中用文字按钮展示 `PDF 文件`、`Word 文件`、`Markdown 文件`。
- 每个产物作为 metadata artifact 持久化，点击后再用右侧面板预览。
#### 问题 8：Markdown 任务列表复选框不能继承全局输入框样式

发生了什么：

- 生成文档里出现了多个异常大的空白方框，看起来像多出来的占位框。
- 实际原因是 Markdown/GFM 的 `- [ ]` 被渲染成 checkbox，而项目全局 `input` 样式把普通输入框的宽度、min-height、padding 等规则套到了这些 checkbox 上。

为什么错：

- Markdown 渲染区是内容展示面，不应该继承表单输入区的布局规则。
- 文档预览一旦出现大空框，会让老师误以为 AI 生成了未知控件或文档排版损坏。

下次如何改：

- `.markdown input[type="checkbox"]` 必须单独限定为紧凑尺寸，例如 14px，并清掉全局 input 的 padding、min-width、min-height。
- 对富文本、Markdown、文档预览、消息气泡这类“内容容器”，新增控件样式时先检查是否会被全局 form CSS 污染。
#### 问题 9：文档预览分界线不能固定死

发生了什么：

- 打开生成文档后，中间对话框和右侧文档预览之间的宽度固定，用户无法按当前任务调整阅读空间。

为什么错：

- 产物预览和对话上下文经常需要并排比较，固定宽度会让一边过窄，尤其是长 Markdown、Word/PDF 草稿预览时。
- 参考 Codex / ChatGPT 的文档展开体验，右侧产物区应当能按阅读需要调整宽度。

下次如何改：

- 右侧 artifact panel 必须有独立 resizer，鼠标拖拽改变右侧面板宽度，同时限制最小和最大宽度。
- resizer 使用 `role="separator"` 和键盘方向键支持，避免只支持鼠标。

### 2026-07-28：Agent Runtime v1 落地复盘
#### 问题 1：坏编码字符串会让局部 patch 非常脆弱

发生了什么：

- `agent-loop.ts` 和 `main/index.ts` 中存在历史中文乱码字符串，局部精确 patch 多次无法匹配，且 `index.ts` 里有疑似未闭合字符串风险。

为什么错：

- Agent runtime 是核心入口，继续围绕坏字符串做小补丁会把语法风险留到后面，且每次修改都难以审查真实差异。

下次如何改：

- 对小而关键、已被编码污染的文件，优先整体重写为干净 UTF-8；大文件则只在必要时整体替换，并立刻用 `tsc --noEmit` 和 smoke 验证。

#### 问题 2：失败状态也必须有可审计事件

发生了什么：

- 旧流程在缺少 DeepSeek API Key 或空输入时直接返回失败对象，没有 agent run，也没有落库事件。

为什么错：

- 世界级 Agent 的失败同样是状态机的一部分。没有 run/event，老师只能看到“失败了”，不能知道失败发生在输入校验、配置、工具还是模型阶段。

下次如何改：

- 所有入口先创建 run；任何 early return 都要写入 guardrail / failure event，并调用 `completeAiAgentRun` 写终态。

#### 问题 3：验收脚本不应依赖外部模型

发生了什么：

- Agent Runtime v1 需要验证工具事件落库，但如果通过 DeepSeek smoke 做，会受 API Key、网络和模型响应影响。

为什么错：

- Runtime 持久化是本地工程能力，应该可重复、快速、无外部依赖；否则会把模型不可用误判为 runtime 失败。

下次如何改：

- 本地 loop / router / schema / persistence 的验收优先写纯 Node smoke；只有验证模型协议时才调用 live API。

### 2026-07-28：Tool Calling v1 落地复盘
#### 问题 1：工具注册和工具执行不能是两套逻辑

发生了什么：

- 早期 `compileAiContext()` 直接按 route 顺序读取上下文，如果后续再给模型加一套 tool-call 执行器，容易出现“deterministic 读取能过、模型工具调用被拦/行为不同”的双轨问题。

为什么错：

- 世界级 agent 的工具层必须有单一事实来源：同一份注册表、同一份 allowlist、同一套参数校验和同一套输出边界。

下次如何改：

- deterministic context compiler 也必须调用 `executeAiToolCall()`，不能绕过 `reviewModelToolCall()`。

#### 问题 2：工具输出必须先 bounded，再考虑发给模型

发生了什么：

- 学习记录可能包含很长正文，如果原样作为 tool result 发回模型，会放大 token、隐私和性能风险。

为什么错：

- Tool Calling 的危险不只在“能不能调用”，还在“调用结果带出去多少”。教育场景尤其要控制学生数据和本地资料上下文。

下次如何改：

- 每个工具 descriptor 必须声明 `maxOutputChars`；执行器返回 `modelResult` 前统一做 bounded payload，并在截断时标记 `truncated=true`。

#### 问题 3：live API 和本地工程验收要分层

发生了什么：

- 本轮接入了 DeepSeek tool-call 消息循环，但没有执行真实 live tool-call 请求。

为什么这样做：

- Tool schema、allowlist、参数校验、执行器和 bounded output 是本地可确定验收的工程能力；live API 受 key、网络、模型策略影响，不能替代本地门禁。

下次如何改：

- 保留 `npm run test:ai-tool-calling` 作为本地门禁；后续如要验证 live tool-call，单独加 DeepSeek live smoke，并明确需要 API Key。

### 2026-07-28：小智 Agent loop 改造复盘

#### 问题 1：前端拼装 trace 会把真实工具过程伪装成思考

发生了什么：

- 原先 AI 回复里的“任务识别 / 上下文装配 / 结构校验”主要由 renderer 的 `buildAiTrace()` 根据结果事后拼装。

为什么错：

- 世界级 agent 的可解释过程应该来自执行器事件，而不是 UI 对结果的装饰。
- 前端拼 trace 容易让工具状态、模型失败、schema 失败混在一起，老师无法判断小智到底做了什么。

- route、plan、tool_call、observe、reflect、finalize 必须在主进程 agent loop 中产生，并随 harness 返回。

为什么错：

- 这类临时验证如果不控制编码，会制造假阴性，让人误以为 router 规则失败。

下次如何改：

- Node/PowerShell 临时脚本涉及中文 prompt 时，优先用 UTF-8 文件、项目测试用例或 Unicode escape。
- 如果 dry-run 结果和正式 eval 矛盾，先排查输入编码，再改业务代码。

为什么错：

- 中控台 AI 的职责是理解任务并调度软件能力；明确学生引用应先尝试本地学生解析，再决定是否需要老师补充。

下次如何改：

- 学生相关 route 默认包含 `resolve_student_reference`。

### 2026-07-28：Confirmation Queue v1 落地复盘

#### 问题 1：AI 写入必须和老师手动写入分流

发生了什么：

- 项目已有 `generateReview()` 手动生成复盘报告，会直接写 `review_reports` 和报告 md 文件。
- Confirmation Queue 要解决的是“小智/模型发起写入”，不是把老师主动点击的旧功能全部拦住。

为什么这样做：

- 老师手动按钮是显式写入意图；AI 回复里的“保存/月报草稿”属于代理写入，风险更高。
- 如果把旧功能也强行改成确认队列，会扩大变更面，影响既有复盘页面验收。

下次如何改：

- 每次接入新写入动作前先区分入口：老师显式操作、AI 草稿、AI 自动执行三类。
- 只有 AI 发起的写入默认必须进 `ai_confirmation_items`。

发生了什么：

- TypeScript 检查指出确认执行返回的 `readback` 理论上可能为空。

为什么重要：

- 只把确认项状态改成 `confirmed` 但没有业务记录，是最危险的假成功。
- 教育场景中报告、标签、题组都要能追溯到真实本地记录。

下次如何改：

- 每个确认动作都必须定义 readback 目标。
- `confirmed` 状态只能在业务表写入成功且读回通过后设置。

#### 问题 3：确认队列 v1 必须保持动作白名单极窄

发生了什么：

- 本轮只开放 `create_review_report`，没有顺手开放学习记录、标签、知识图谱、题组写入。

为什么这样做：

- 写入动作的破坏性不同；过早开放多个动作会让确认 payload、回滚策略和 UI 审查都变复杂。

下次如何改：

- 新增每一种写入动作时都配一个本地 smoke：创建不写库、拒绝不写库、确认后只写一次、读回一致、重复执行失败。

### 2026-07-28：SubIntent Router + Structured Reply v2 复盘

#### 问题 1：二级意图的难点不是枚举，而是优先级冲突

- 如果只叠关键词，router 会继续出现“看似有规则，实际不会分发”的问题。

下次如何改：

- router 规则必须按安全/工作台、明确学生诊断、明确练习生成、错因分析、备课、知识检索的优先级审查。
- 每加一个关键词都要补一条例外 eval，避免抢走其他 route。

#### 问题 2：学生名抽取不能贪婪

发生了什么：

- 旧正则把“小A和小B”识别成一个学生引用，导致多学生歧义没有触发澄清。

为什么错：

- 多学生任务如果误当成单学生，会把对比、分别生成、分别报告等任务执行成错误对象。

下次如何改：

- 学生名抽取优先匹配短显示名，如 `小A`、`小B`、`小明`，并过滤“小智/小智能”等 AI 自称。
- 任何多学生引用先只问一个关键澄清问题，不自动分别读取两名学生记录。

#### 问题 3：Structured Reply v2 必须有本地失败用例

发生了什么：

- v2 不只是新增字段，而是增加了 route-specific 校验和 repair loop。

为什么重要：

- 如果没有本地 smoke，模型输出看起来是 JSON 就可能被当作成功，继续产生“回复完整但没意义”的问题。

下次如何改：

- 每次升级 schema 都要写坏例子：route mismatch、缺事实、缺边界、坏产物结构、写入缺确认。
- repair 只能修 JSON 和缺字段，不能借 repair 机会重新调用工具或编造证据。

### 2026-07-28：Education Grader 与三元题组闭环 v1 复盘

#### 问题 1：合法 JSON 不等于教育可用

发生了什么：

- `xiazhi.reply.v2` 已能约束字段和 route-specific 结构，但仍可能出现“建议上传资料”“学生就是不努力”这类看似完整、实际不可用或有风险的回答。

为什么错：

- 教育 Agent 的失败经常不是语法失败，而是证据缺口、标签化语言、隐私边界和写入边界失败。

下次如何改：

- schema 通过后继续跑 Education Grader；critical 问题必须 fail-closed。
- Grader bad-case 要作为本地 smoke 保留，避免后续 prompt 或 schema 改动让无意义回复混过。

#### 问题 2：题库检索不能把多词查询当成一个完整短语

发生了什么：

- `npm run test:ai-exercise-set` 第一次失败：题库里有“一次函数”和“斜率”，但检索 `"一次函数 斜率"` 没命中。

为什么错：

- 直接用完整 query 做 `LIKE '%一次函数 斜率%'` 对教师自然语言不友好，也会让本地题库“看似有数据但召回不到”。

下次如何改：

- 本地关键词检索先做 token 化，多个 token 用 OR 命中；后续再补更可靠的 FTS/embedding。
- 三元题组 smoke 必须包含多 token 检索，不只测单词。

#### 问题 3：Windows SQLite 临时目录清理可能有句柄延迟

发生了什么：

- 新 smoke 业务断言通过后，清理临时数据根时出现 `EPERM`。

为什么错：

- Windows 上 sqlite3 句柄和 WAL 文件释放有短暂延迟，如果脚本立即递归删除目录，可能误报失败。

下次如何改：

- smoke 内部用 `finally` 关闭 store。
- 删除临时目录时加 `maxRetries` / `retryDelay`，避免把清理时序误判为业务失败。

#### 问题 4：写入动作扩展仍要坚持极窄白名单

发生了什么：

- 本轮把确认队列从 `create_review_report` 扩展到 `save_exercise_set`，没有顺手开放学生标签、学习记录或知识图谱写入。

为什么这样做：

- 每一种写入动作都需要单独 payload、确认预览、执行器、readback 和重复执行保护。

下次如何改：

- 新增写入动作必须配套 smoke：创建不写库、拒绝不写库、确认后只写一次、readback 一致、重复确认失败。

### 2026-07-28：错题图片与脱敏链路 v1 复盘

#### 问题 1：没有 OCR 文本时不能假装完成

发生了什么：

- Phase 8 第一段没有直接接真实 OCR，而是先接图片托管、解析状态、脱敏和老师修正。

为什么重要：

- 教育 AI 最容易出现“流程走完但没有有效信息”的假成功；无 OCR 文本时如果显示为已分析，会把老师带到错误结论。

下次如何改：

- 无解析文本必须明确进入 `needs_ocr`。
- UI 后续要把 `needs_ocr` 显示成待处理任务，而不是失败或成功答案。

#### 问题 2：脱敏不能破坏题目本身

发生了什么：

- smoke 同时放入学生名、手机号、身份证号、邮箱和数学题干，验证隐私被移除但“一次函数”“斜率”等题目内容保留。

为什么重要：

- 脱敏如果过度，会让模型拿不到可分析的题目；脱敏如果不足，会破坏本地优先和隐私边界。

下次如何改：

- 每新增一种 PII 规则都要加反例：隐私应移除，学科关键内容应保留。
- 后续接 OCR 后要用真实错题图片样本做人工复核，不只测手写字符串。

#### 问题 3：错题图片链路必须用真实附件导入验收

发生了什么：

- smoke 先创建临时 PNG，再通过 `importAttachments()` 进入本地学生数据目录，然后基于导入后的 attachment 建 analysis。

为什么这样做：

- 直接传字符串路径无法验证“原始图片不自动上传”和“路径必须留在 managed data root”这两个核心安全边界。

下次如何改：

- 附件、OCR、脱敏、模型分析相关测试都应从真实本地文件入口开始。
- 任何从 renderer 传来的路径都必须由主进程重新校验，不能信任前端。

### 2026-07-28：知识库/图谱增强 v1 复盘

#### 问题 1：知识库命中不等于可引用证据

发生了什么：

- 旧版 `search_teacher_knowledge` 只返回 chunk 预览，模型很容易把任何命中都当成同等强度的证据。

为什么错：

- 教育场景里，“资料里出现过”与“可以支持教学判断”不是一回事；尤其图谱节点只是关系摘要，不能替代正文证据。

下次如何改：

- chunk 必须携带 `evidenceStrength`、`qualityScore`、`sourceTrust` 和 sourceId。
- 图谱工具必须明确说明节点/边是背景关系，不是正文直接证据。

#### 问题 2：知识库也可能包含学生隐私

发生了什么：

- smoke 特意导入含手机号和邮箱的 markdown，验证工具层只返回元数据，不返回正文预览。

为什么重要：

- 老师资料并不天然安全，备课资料、个案笔记、错题讲义里都可能夹带个人信息。

下次如何改：

- 每种新解析器都要继承 `containsPersonalData` 检测和工具层隐藏策略。
- 后续脱敏规则扩展后，知识库 smoke 要同步加入新 PII 样本。

#### 问题 3：图谱边必须可审计

发生了什么：

- Phase 9 为 `knowledge_edges` 增加了 `evidenceKind` 和 `evidenceStrength`，并在 smoke 中验证至少存在 `direct_quote` 边。

为什么重要：

- 没有 evidenceKind 的图谱边只是“看起来智能”的关系线，无法解释它来自正文、元数据还是推断。

下次如何改：

- 后续任何自动抽取边都必须写明来源 chunk、证据文本、证据类型和置信度。
- 写入知识图谱关系若来自 AI 推断，应先进入老师确认队列。

### 2026-07-28：真实文档导出 v1 复盘

#### 问题 1：UI 预览入口不能冒充真实导出

发生了什么：

- 旧版 AI 产物面板已经显示 PDF/Word/Markdown 卡片，但导出按钮只是提示“后续接入管线”，没有真实文件。

为什么错：

- 对老师来说，“可预览”和“已导出”是两个完全不同的状态；如果 UI 用话术替代文件，会让小智看起来像在完成任务，实际没有交付。

下次如何改：

- 所有导出类能力都必须经过主进程真实写文件、计算 hash、记录状态、readback 后才能显示成功。
- smoke 必须验证文件存在、大小、格式魔数和失败路径，不能只测按钮渲染。

#### 问题 2：文档格式生成要先定义 v1 边界

发生了什么：

- 本轮没有引入重型依赖，而是实现最小 PDF writer 和最小 DOCX zip+xml writer，通过 smoke 验证 `%PDF-`、`PK` 和 `word/document.xml`。

为什么重要：

- Phase 10 的关键目标是打通真实文件闭环，而不是一次性追求 Word/PDF 的完美排版；但也不能把 HTML 或字符串假装成 docx/pdf。

下次如何改：

- v1 可接受最小有效文件，但必须在 Memory/Wiki 中明确边界：中文字体、分页、表格、图片、公式和模板样式还不是完成态。
- 后续增强排版时继续沿用 `document_artifacts` 的状态/hash/readback 口径。

#### 问题 3：历史产物状态需要单一事实来源

发生了什么：

- 当前 UI 导出后会更新面板状态，但历史消息 metadata 尚未自动回写导出结果。

为什么重要：

- 如果同一个 artifact 同时存在消息 metadata 和 `document_artifacts` 两份状态，就可能出现历史对话显示“未导出”，但数据库里已有真实文件的割裂。

下次如何改：

- Phase 10 v1.1 或 Phase 11 应在打开历史会话时按 artifact id 合并 `document_artifacts` readback，或在导出成功后更新对应 assistant message metadata。

### 2026-07-28：README 功能展示复盘

#### 问题 1：对外 README 容易把路线图写成完成态

发生了什么：

- README 需要展示当前功能和 UI 页面，但项目同时有很多 Phase 规划与 v1 能力边界。

为什么重要：

- 新读者会把 README 当作项目真实状态入口；如果把“真实 OCR”“复杂 PDF/DOCX 排版”“Graph RAG”“完整题库导入 UI”等规划能力写成完成态，会误导后续验收和开发优先级。

下次如何改：

- README 功能表必须明确状态列，使用“已落地”“v1 已落地”“当前边界”等词。
- README 的功能说明优先引用 `2.Memory.md` 的真实完成记录，不凭愿景扩写。
- 每次新增阶段能力后，同步检查 README 是否需要更新验证命令、UI 页面说明和边界说明。

### 2026-07-28：Observability / Regression v1 复盘

#### 问题 1：回归报告不能靠静态结论

发生了什么：

- Phase 11 把报告生成建立在 SQLite 真实 run/event/tool/artifact/confirmation/task 数据上，再根据数据生成 gate。

为什么重要：

- 小智的可靠性不能只靠“测试通过”文字说明；必须能回看具体 run、工具轨迹、导出状态、确认队列和预算指标。

下次如何改：

- 新增 gate 时先明确数据来源表和失败条件，再写 UI。
- 报告 UI 只能展示数据库 readback，不要前端临时拼状态。

#### 问题 2：推送后还要再查工作区

发生了什么：

- README 提交推送后，工作区继续出现 Observability 相关本地改动，需要二次检查、验证和提交判断。

为什么重要：

- 多阶段开发中，迟到的本地改动如果不检查，容易出现“远端已推送但本地还有关键代码”的断层。

下次如何改：

- 每次 push 后立刻执行 `git status --short --branch`。
- 若有未提交代码，必须确认是否属于本轮目标；属于则补验证和补提交，不属于则明确留在工作区。

### 2026-07-28：Observability + Regression v1 复盘

#### 问题 1：测试绿不等于可追溯

发生了什么：

- 过去每个阶段都有 smoke，但如果没有统一报告表，后续只能从终端输出里回忆“当时过了什么”。

为什么错：

- 小智是教育 Agent，回归能力必须能被读回和审计；终端输出不是稳定产品状态。

下次如何改：

- 回归报告必须写入 `ai_regression_reports` 并 readback 验证。
- 发布前门禁不只跑 eval，还要生成 telemetry snapshot 和 gate 列表。

#### 问题 2：缺数据不能静默通过

发生了什么：

- latency、tool trace、usage 等指标不是每条历史数据都一定存在。

为什么重要：

- 如果把缺失指标当作通过，会让“看起来可观测”替代真实可观测。

下次如何改：

- release-critical 直接失败，辅助指标缺失明确 warning。
- final 说明中必须报告 warning 边界，不能包装成完全无风险。

#### 问题 3：预算指标需要上游持续写入

发生了什么：

- token/context 预算当前从 `ai_tasks.result_json.usage` 和 `payload_json` 聚合。

为什么重要：

- 如果 DeepSeek live 或后续工具链不持续写 usage/payload，预算报告会变成局部样本。

下次如何改：

- 后续接 live API、工具执行或批处理任务时，同步写入 usage、sourceCount、knowledgeSnippetCount、graphNodeCount 等字段。
- 新增任务脚本时要补一个预算字段断言，避免指标长期漂移。

### 2026-07-29：Phase 12 教师可用性打磨 v1 复盘

#### 问题 1：可用性不能只靠 prompt 文案

发生了什么：

- 小智之前即使已经有 router、schema 和教育 grader，最终回复仍可能变成固定流水线话术，甚至把“请手动切学生数据”当成正常答案。

为什么重要：

- 教育 Agent 的智能感首先来自“能自己分发任务并给老师可执行结果”，不是把内部流程念给老师听。
- 只改 system prompt 很容易回退；必须把退化话术、过长泛答、写入缺确认变成 deterministic gate。

下次如何改：

- 改 prompt 的同时补本地 grader 和 smoke；没有门禁的“口吻优化”不算完成。
- 每个 route 都要有长度、下一步数量和展示段落的可用性预算。

#### 问题 2：schema 字段不等于 UI 段落

发生了什么：

- `xiazhi.reply.v2` 需要 facts/evidence/inferences/unknowns 等字段用于校验和审计，但直接把所有字段渲染成“事实/证据/推断/未知”会让普通任务像模板报告。

为什么重要：

- 结构化是给系统做约束的，可读回复是给老师用的；两者不能混为一谈。

下次如何改：

- formatter 按 route 选择段落：普通问答短答，学生诊断保留依据和教学判断，写入/产物只突出确认和入口。
- 新增 schema 字段时先问“它是否应该被老师看见”，而不是默认渲染。

#### 问题 3：降噪不等于隐藏关键风险

发生了什么：

- Confirmation Queue 从展示 3 个改为展示 2 个并折叠剩余项，减少老师被待确认卡片打断。

为什么重要：

- 老师工作台需要低打扰，但 AI 写入仍必须确认前不落库；降噪不能变成自动确认或静默忽略。

下次如何改：

- 折叠项只做提示，不自动执行。
- 后续做确认队列筛选时，必须保留 pending/confirmed/rejected/readback 的真实状态。

### 2026-07-29：Phase 12 v1.1 可用性样本与回归整合复盘

#### 问题 1：proxy 样本不能冒充真实老师评分

发生了什么：

- 本轮新增 25 条代表性教师任务 proxy 样本，用于防止小智回复退回模板化、绕路和缺确认。

为什么重要：

- proxy 样本能证明规则和 formatter 没回退，但不能证明真实老师愿意每天用。
- 如果把 proxy 通过写成“教师人工评分 >= 4/5”，后续产品验收会失真。

下次如何改：

- 文档必须持续区分 proxy eval、模型 grader、真实老师人工评分。
- 真实老师评分必须记录 `teacherScore`、`needsRewrite`、`roundsToUseful`、`mainIssueCode` 和老师备注。

#### 问题 2：可用性分数要进入真实 readback

发生了什么：

- 本轮把 `harness.usabilityGrade` 摘要写入 `ai_tasks.result_json`，再由 `buildAiTelemetrySnapshot()` 聚合。

为什么重要：

- 如果只在 smoke 里打印分数，回归报告无法追踪质量漂移。
- 小智的“变聪明”必须能在 SQLite 报告中被证明，而不是靠终端输出回忆。

下次如何改：

- 新增质量指标时，先确定写入位置、聚合口径和 gate 失败条件。
- 历史数据缺字段只能 warning，不能补假分数。

#### 问题 3：质量 gate 需要同时看样本集和真实任务

发生了什么：

- `usability_eval_baseline` 验证 proxy 样本集，`usability_quality_gate` 验证真实 AI console task 是否有可用性评分且达标。

为什么重要：

- 只看样本集会过拟合；只看真实任务又可能样本不足。

下次如何改：

- 发布前至少同时跑 `test:ai-usability` 和 `test:ai-observability`。
- 后续接真实老师样本后，把人工评分统计作为第三类 gate。

### 2026-07-29：Phase 12 v1.2 教师人工评分基础设施复盘

#### 问题 1：人工评分必须是可回读数据，不是 smoke 输出

发生了什么：

- 本轮新增 `ai_usability_reviews` 和 `humanUsability` summary，把 teacherScore、needsRewrite、roundsToUseful、mainIssueCode 等字段写入 SQLite 并纳入 regression gate。

为什么重要：

- 如果评分只存在于脚本断言或终端输出，后续无法追踪质量漂移，也无法和真实老师样本对账。
- 小智的“更聪明”必须能从本地数据库、snapshot 和回归报告一路读回来。

下次如何改：

- 新增任何质量指标都必须明确：写入表、聚合函数、回归 gate、readback smoke。
- UI 表单/CSV 导入只调用同一套 Store/IPC，不另建一套评分口径。

#### 问题 2：seeded human review 不是外部真实老师样本

发生了什么：

- `test:ai-human-review` 使用 seeded 样本验证基础设施，平均分达到 4，但这些不是外部老师真实使用后的独立评分。

为什么重要：

- seeded 样本可以证明工程链路正确，不能证明产品可用性已经被真实老师接受。
- 若把 seeded 样本写成最终验收，会让 Phase 12 的判断失真。

下次如何改：

- 文档和最终汇报必须区分 `proxy eval`、`seeded human-review smoke`、`真实老师人工评分`。
- 只有真实老师样本进入 `ai_usability_reviews` 且平均分、返工轮次达标，才勾选最终验收。

#### 问题 3：live replay 的 skipped 也是结果，但不是 live 通过

发生了什么：

- `test:ai-live-usability` 在没有 `DEEPSEEK_API_KEY` 时明确输出 skipped。

为什么重要：

- 这能保证本地无 key 环境也能跑完整门禁，同时防止把未执行的线上模型调用说成已经验证。

下次如何改：

- 对所有依赖外部 key / 真实服务的 smoke，都必须同时报告 `skipped` 原因和未验证边界。
- 配好 key 后再把 live replay 输出、模型版本、token usage 和人工评分样本绑定到同一轮验收记录。

### 2026-07-29：Phase 12 v1.3 人工评分 UI 复盘

#### 问题 1：UI 表单也必须证明写到同一套后端口径

发生了什么：

- 本轮没有只做静态表单，而是让设置页表单和 CSV 导入都调用 preload 的 `createAiUsabilityReview()`，并用 Electron smoke 从 `getAiUsabilityReviewSummary()` 回读。

为什么重要：

- 如果 UI 只在 React state 里显示“已保存”，人工评分就不能进入 regression gate，也无法支撑教师可用性验收。

下次如何改：

- 任何质量录入 UI 都必须配一个 UI smoke：真实打开页面、真实提交、真实从 SQLite/preload 回读。
- 表单字段新增或改名时，同步改 CSV parser、rubric 文档和 smoke。

#### 问题 2：CSV 导入不能绕过主进程校验

发生了什么：

- CSV / TSV 文件读取使用浏览器 FileReader，解析后仍逐条调用主进程 Store API；没有在 renderer 直接写数据库。

为什么重要：

- 人工评分是质量门禁输入，不能因为“批量导入方便”就绕过 1-5 分、轮次范围、必填 prompt 等校验。

下次如何改：

- 批量导入只负责解析和提示，数据合法性继续由 Store 层把关。
- 后续做 Excel/CSV 正式导入时，需要增加部分失败/部分成功的明细反馈，避免第一条坏数据中断时老师不知道导到哪里。

#### 问题 3：失败样本回放要从“重新运行”走向“对比实验”

发生了什么：

- 当前失败回放先把低分或需重写样本放回 AI 输入框，方便老师重新运行。

为什么还不够：

- 这只是回放入口，还没有把原回复、新回复、二次评分、模型版本和 prompt 版本绑定起来。

下次如何改：

- 下一步应建立失败样本 replay 记录：oldReviewId、newRunId、newReviewId、model、promptVersion、before/after 分数。
- 回归报告应能展示“修复后失败样本是否真的变好”，而不只是列表可点击。

### 2026-07-29：Phase 12 v1.4 before/after replay experiment 复盘

#### 问题 1：改善幅度不能由 UI 乐观计算

发生了什么：

- 本轮新增 `ai_usability_replay_experiments`，但分数、轮次、issue delta 不重复写入实验表，而是通过 join before/after 两条 `ai_usability_reviews` 回读计算。

为什么重要：

- 如果 UI 在保存时把 delta 算好并展示，后续老师修正任一 review 后，实验列表和真实评分会漂移。
- 可用性改造要能经得起对账：review rows、replay summary、telemetry snapshot、regression gate 必须一致。

下次如何改：

- 新增任何“改善/趋势/命中率”指标，优先从源数据 readback 聚合，不把派生结论当源数据永久写死。
- smoke 必须覆盖 create、list、summary、snapshot、gate 五层，而不是只断言 UI 文案。

#### 问题 2：replay gate 默认 warning，release gate 要显式加阈值

发生了什么：

- `usability_replay_improvement_gate` 在没有 replay 实验时默认 warning；调用方设置 `minimumReplayExperimentCount` 或 `minimumReplayImprovementRate` 后才形成强 gate。

为什么重要：

- 人评基础设施 smoke 不一定 seed replay；如果新 gate 默认 failed，会让无关测试变红。
- 但发布或专项验收时必须显式要求 replay 数量和改善率，否则无法证明失败样本真的修复。

下次如何改：

- Observability smoke 这类全量 gate 应 seed replay 实验并要求全部 passed。
- 专项脚本可以保留 warning，用于提醒“这个脚本只验证该层能力，不代表完整可用性验收”。

#### 问题 3：before/after 工程链路仍不是外部老师验收

发生了什么：

- `test:ai-replay` 和 UI smoke 都使用 seeded before/after 样本，能证明工程闭环，但不能证明真实老师返工量下降。

为什么重要：

- v1.4 解决的是“能记录和量化改善”，不是“已经真实改善”。
- 如果把 seeded replay 写成最终验收，会重复 v1.1 proxy 样本的口径风险。

下次如何改：

- Phase 12 v1.5 必须让外部真实老师样本进入同一张 review/replay 表，并绑定 live DeepSeek 输出、模型版本、promptVersion 和 token usage。
- 最终验收只看真实老师样本的平均分、返工轮次、改善率和常见任务 1-2 轮完成率。

### 2026-07-29：Phase 12 v1.5 模型 grader proxy 复盘

#### 问题 1：model grader proxy 不能冒充真实 LLM-as-judge

发生了什么：

- 本轮接入了 `ai_model_grades`、六维评分、年级适切维度、telemetry 和 `model_grader_quality_gate`。
- 当前评分器是 deterministic proxy，用于稳定捕获退化话术、无证据回答、不安全学生标签和缺少可执行下一步。

为什么重要：

- proxy grader 适合作为快速回归门禁，但它不能代表外部模型裁判，也不能证明真实老师满意。
- 如果文档把 proxy 写成 LLM-as-judge 已完成，后续会误以为 Phase 12 最核心的真实质量验证已经结束。

下次如何改：

- 所有模型裁判样本都写入 `ai_model_grades`，并用 `graderMode` 区分 `deterministic_proxy` 与 `llm_judge`。
- 最终验收必须同时看真实老师样本、live DeepSeek 输出、真实 LLM-as-judge 和 replay 改善率。

#### 问题 2：坏样本可以用于校验识别能力，但不能污染通过门禁

发生了什么：

- `test:ai-model-grader` 里对坏样本执行 proxy grade，确认能命中关键 issue，但没有把坏样本写入用于 passing gate 的 seeded 数据集。

为什么重要：

- 如果把刻意构造的坏样本写进同一轮 passing summary，专项 smoke 会因为预期失败样本而让 release gate 失败。
- 如果完全不跑坏样本，又无法证明 grader 真能抓住“小智弱智回复”的核心退化。

下次如何改：

- 对质量类 smoke 区分“识别能力检查”和“通过门禁样本”；前者断言 issueCodes，后者断言 snapshot/gate。
- Observability 全量 smoke 只 seed 应通过样本，并用单独坏样本断言覆盖失败模式。

#### 问题 3：年级适切不能只保存总分

发生了什么：

- 本轮把 gradeAppropriatenessScore 作为独立维度写入表、summary 和 gate，而不是只写 overall。

为什么重要：

- 教育 AI 的“答得对”不等于“适合这个年级的老师拿去用”；小学、初中、高中的语言、抽象度和步骤粒度差异很大。
- 如果只保留 overall，后续无法定位是证据不足、行动性不足，还是年级适切出了问题。

下次如何改：

- 质量评分继续保留分项：evidence、actionability、safety、gradeAppropriateness、concision、teacherControl。
- 后续接真实 LLM-as-judge 时沿用同一张表和同一批分项，避免趋势口径断裂。

### 2026-07-29：Phase 12 v1.6 live evidence binding 复盘

#### 问题 1：live-ready 证据绑定不能写成 live API 已验收

发生了什么：

- 本轮把同一条 `runId` 贯穿 after review、replay experiment、model grade、telemetry 和 regression gate。
- 但本轮没有配置 `DEEPSEEK_API_KEY` 执行真实线上 DeepSeek 回放，也没有外部老师真实样本。

为什么重要：

- 证据链不断裂是质量验收的前置条件，不是质量验收本身。
- 如果把 seeded run 说成真实 live，就会掩盖后续最关键的 API、样本和人工复核风险。

下次如何改：

- 文档和交付说明必须明确区分 seeded/live-ready、真实 DeepSeek live、外部老师人工评分和真实 `llm_judge`。
- 配好 key 后再运行 `npm run test:ai-live-usability`，并把 live 输出绑定到同一套 review/replay/model-grade 表。

#### 问题 2：runId、promptVersion、token usage 必须落库，不能只在终端里看

发生了什么：

- v1.6 把 `runId`、`sessionId`、`promptVersion`、`totalTokens` 写入 `ai_model_grades`，并让 replay summary 统计 `liveLinkedCount`。

为什么重要：

- 质量回归最终要比较同一类任务在不同 prompt/model/version 下的改善；如果这些字段只存在于脚本日志，趋势和追责都会断。
- token usage 是成本和上下文预算的一部分，不能在模型裁判阶段丢失。

下次如何改：

- 后续新增真实 `llm_judge` 或 live replay 时沿用同一写入口，不另建临时表或 renderer state。
- 新质量门禁必须先看 SQLite readback，再判断 gate。

#### 问题 3：live evidence gate 应支持 release 阈值，而不是只做提示

发生了什么：

- `live_evidence_binding_gate` 默认在没有绑定样本时给 warning；当调用方传入最小绑定数量时可升级为 failed。

为什么重要：

- 开发环境可能暂时没有真实样本，默认 warning 能保持本地 smoke 可运行。
- 发布前必须显式设置阈值，否则“没有绑定证据”会被误读成“不影响发布”。

下次如何改：

- 发布前一键门禁应传入 `minimumLiveLinkedReplayCount`、`minimumRunLinkedModelGradeCount`、真实老师最小样本数和最低平均分。
- v1.7 做评分趋势图时，把 gate 阈值和趋势统计放到同一份回归报告里。

### 2026-08-10：DeepTutor 融合调研教训

#### 问题 1：route allowlist 不能被当成固定执行计划

- 当前 `runAiAgentLoop()` 会把 route 允许的工具全部预执行，因此不同问题看起来都走同一条流水线。
- allowlist 应只定义“最多能调用什么”；真正执行哪些工具必须由 loop 根据当前观察逐轮决定。
- 改造时应先取消预执行语义，再接多轮 loop，否则只是在固定流程外包一层 Python。

#### 问题 2：不能把 DeepTutor 整个产品当成一个组件复制

- DeepTutor 同时包含 Python runtime、Next.js UI、多用户、PocketBase、RAG、Memory、Partners 和大量工具。
- 全量嵌入会产生双 UI、双设置、双会话和双数据真源；TypeScript 全量重写又会丢失上游维护收益。
- 最合适的边界是 Electron 宿主控制面 + 固定版本 Python Capability sidecar，且所有业务工具回调宿主审核。

#### 问题 3：DeepTutor thinking 事件不能直接满足“展示思考过程”

- 部分 pipeline 会把 LLM chunk 发到 thinking channel，其中可能包含草稿推理或敏感上下文。
- Omni-Edu 只能展示可验证执行摘要，不能原样展示或持久化隐藏推理链。
- 必须在 bridge 层做事件分类、redaction、聚合和可见性标记，而不是直接转发 StreamBus。

#### 问题 4：掌握学习的智能部分和门禁部分要分开

- 模型适合决定怎么讲、问什么、是否需要换一种解释。
- 掌握阈值、一次答对上限、错题优先、复习到期和重规划次数应由确定性引擎计算。
- 这种分工既保留 Agent 自主性，也避免把模型印象写成永久学生结论。

#### 问题 5：上游复用必须先固定版本和许可证证据

- DeepTutor 发布频繁，直接跟随 main 会让 bridge 和测试不断漂移。
- 应固定 commit、保留 LICENSE/notices、记录 patch，并用 parity/contract/adversarial tests 控制升级。

#### 问题 6：完整盘点不能等同于全部迁移

- DeepTutor 的核心产品与平台能力按可交付粒度实际形成 77 项，包含 runtime、学习、内容、知识、扩展与平台六个域；源码目录交叉审查补出了 ExploreContext、Vision Solver 和原生 Obsidian Capability 三个 README 概览不够显眼的模块。
- 全部纳入台账是为了避免漏项和后期隐性依赖，不代表 MCP、CLI Apps、伙伴通道、多用户、高级 RAG、媒体生成都适合当前教师桌面端。
- 应明确 A/B/C/D 处置并给每项统一 DoD；否则“行业领先”会退化为功能数量竞赛和双数据真源。

#### 问题 7：2 秒性能必须按阶段定义

- 外部大模型与深研究无法保证 2 秒内完成全文，若把加载动画当成完成指标会产生虚假验收。
- 应分别记录 run 创建、首个可见事件、首 token、本地工具、provider 等待和最终完成时间。
- 长任务在 200 ms 内返回 runId、500 ms 内展示真实进度；常规在线问答首 token 目标 p95 不超过 2 秒，最终完成另行统计。

### 2026-08-10：DeepTutor DT-0 真实源码复用复盘

#### 问题 1：协议 mock 不能冒充 AgentLoop 集成

发生了什么：

- 首版 bridge 只返回固定 mock 事件，虽然能验证取消、重复启动和帧限制，但没有执行 DeepTutor 源码。
- 本轮改为固定 commit 的机械 vendor，并让 chat dry-run 真正导入 `AgentLoop`、`UnifiedContext` 和 `StreamBus`；Fake OpenAI stream 只隔离网络依赖。

为什么重要：

- 用户要求“用轮子”，所以必须能指出运行时实际调用了哪个上游类和哪个 commit。
- 协议通过、构建通过不等于上游 loop 可运行；两者需要分开验收。

下次如何改：

- 每个能力包都要有“真实上游源码调用 + 宿主工具边界 + SQLite readback”三段证据。
- 继续保留协议 contract smoke，但新增 capability parity smoke，不能只测试固定响应。

#### 问题 2：后台 sidecar 线程会在 stdin 关闭时丢事件

发生了什么：

- 初次将 AgentLoop 放入后台线程后，Node smoke 关闭 stdin，Python 主循环立即退出，导致正常 turn 没有终态事件。
- 在 bridge EOF 路径等待已启动线程完成，并用 stdout lock 保证 NDJSON 行不交错后，事件序列恢复连续。

下次如何改：

- 正式 supervisor 需要把线程替换成可取消的 asyncio task registry，并将 cancel token 传入真实能力。
- 每次 sidecar smoke 都要断言每个 turn 的 sequence 从 1 连续到 done。

#### 问题 3：Windows 运行时路径和 Playwright API 都可能漂移

发生了什么：

- Python launcher 不能假设 `python` 在 PATH 中，smoke 改为发现 `C:\Python314\python.exe` / `py.exe`。
- Electron smoke 的 Playwright 版本没有稳定提供 `app.process()`，关闭时直接调用会抛异常；改为可选、捕获后以 `app.close()` 为主。

下次如何改：

- 打包配置必须显式携带 Python runtime/依赖探针，并在启动诊断中记录版本而不是静默猜测。
- E2E 脚本对可选 Playwright API 必须做 feature detection。

### 2026-08-11：HostToolProxy 双向协议复盘

#### 问题 1：sidecar 事件判断顺序会吞掉宿主请求

发生了什么：

- 初版 `sidecar-client` 在解析到一行后先判断 `record.type !== 'event'`，导致 `host_tool_request` 永远在回调前被丢弃。
- 修正为先处理 response、host_tool_request，再处理普通 capability event；新增动态 round-trip smoke 后才发现这个问题。

为什么重要：

- “真实工具注册表”必须有真正的 request/result 往返；只声明类型或只执行本地函数不算接通。
- 协议解析器的分支顺序属于安全边界，错误时会表现为 sidecar 永久等待而不是明显异常。

下次如何改：

- 为每一种跨进程消息建立独立 golden fixture 和超时/断连测试；不依赖单个通用 event 分支。
- HostToolProxy result 必须进入 SQLite tool-run/readback，再让 UI 显示“已使用”。

#### 问题 2：同步 stdin + 异步 turn 需要显式 waiter

发生了什么：

- host tool 请求发生在后台 AgentLoop 线程，结果却从主 stdin reader 回来；若没有按 requestId 注册 `Queue`，结果会在 waiter 建立前被丢弃。
- 当前 bridge 用 requestId→Queue、120 秒硬超时和 bounded JSON 结果完成了 deterministic round-trip。

下次如何改：

- 生产实现改成统一 asyncio task registry，并把 cancel token 传给等待中的 host call。
- 超时、sidecar 崩溃和重复 result 必须分别落入 `PROVIDER_*` / `CANCELLED` / `INTERNAL_*` 证据码。

### 2026-08-11：sidecar 事件落库与 renderer 订阅复盘

#### 问题 1：事件落库不能依赖 sidecar sequence 直接作为 SQLite sequence

发生了什么：

- 主进程会先写一条本地 route 事件，sidecar 自己的 sequence 也从 1 开始；若直接把 sidecar sequence 写入 SQLite，会与宿主事件冲突。
- 当前改为每个 turn 绑定一个 promise queue，由 `recordAiAgentEvent()` 在 SQLite 内计算下一个连续 sequence；sidecar sequence 只作为 `outputSummary.sidecarSequence` 留作诊断。

下次如何改：

- 若支持断线重连，必须增加 event idempotency key（turnId + sidecarSequence + phase），避免重放事件重复入库。
- sidecar 崩溃恢复时，先回读 run 的最后事件再决定 resume、blocked 或 failed，不能仅靠 renderer 状态判断。

#### 问题 2：安全事件必须在入库前过滤，而不是只在 UI 隐藏

发生了什么：

- `THINKING` 事件通过 bridge 映射为 `traceOnly` 和固定公共摘要；Electron smoke 进一步验证 `<think>`、`<thinking>` 和 secret-like 文本不进入 SQLite detail。
- blocked HostToolProxy 结果被写成 `observe` 证据，状态仍为 blocked，避免 UI 把“工具未获准”显示成成功。

下次如何改：

- 为每个 event phase 建 golden fixture，明确允许字段、最大长度和敏感字段 redaction；不能把字符串黑名单当成完整脱敏方案。
- 真实模型接入后增加 provider error、工具参数和原始附件路径的专门泄露用例。

#### 问题 3：renderer 订阅完成不等于普通 AI 页面已迁移

发生了什么：

- preload 和 renderer 已能接收 sidecar 安全事件，但当前普通问答提交仍保留原有 DeepSeek 路径；如果只看“时间线有事件”容易误判全链路切换完成。

下次如何改：

- 以一次真实页面提交的 runId、SQLite events、最终回复和工具轨迹做端到端验收，再切换默认入口；保留可观测 fallback 和明确失败原因。

#### 问题 4：AgentLoop 工具调用的参数必须经过 JSON 边界清洗

发生了什么：

- DeepTutor `dispatch_tool_calls()` 会给工具注入 `event_sink` 等执行期 kwargs；直接把全部 kwargs 发送给 HostToolProxy 会触发函数对象 JSON 序列化异常。
- `_HostProxyTool` 现在只提取 schema 允许的标量参数（当前为 `studentName`），再发出跨进程请求；这同时减少了工具参数泄露面。

下次如何改：

- 不要在 sidecar 工具层复制每个业务 schema；从 Omni manifest 生成严格 JSON Schema，并在宿主二次校验未知字段、类型、长度和权限。
- 真实模型接入后必须保留 native tool-call parity smoke，防止 provider 把结构化调用退化成正文 JSON。

#### 问题 5：模型凭证不能随 sidecar 启动环境下发

发生了什么：

- 如果把 `DEEPSEEK_API_KEY` 放进 Python 子进程环境，sidecar 崩溃日志、诊断或未来插件边界都可能扩大凭证暴露面。
- 现在 sidecar 只发送 `xiazhi.model.request.v1`，Electron main 读取 SQLite/env 设置并调用 provider；返回只包含 bounded choices、usage 或错误码。

下次如何改：

- live provider 调用要记录 provider wait、首 token、usage、超时和 retryable 错误，但不能记录 Authorization header 或完整请求正文。
- 多模型接入时在 main 内做 provider registry，sidecar 只看到抽象 model 名称，不看到 key、base URL 私密配置或租户凭证。

#### 问题 6：模型代理失败不能被 AgentLoop 的正常 done 覆盖

发生了什么：

- 初版 `produce()` 捕获 provider 异常并发出 `stream.error`，但外层仍无条件发 `done/succeeded`，导致缺少 API Key 的 run 被错误标成成功。
- `TurnState.failed` 现在会贯穿异常、error event 和 done 终态，Electron SQLite readback 能看到 failed。

下次如何改：

- 所有 Capability 都要有“异常 → error → failed done → failed run”对抗样例；不能只测试成功终态。

### 普通入口切换的验收结论（2026-08-11）

- `runDeepTutorConsole` 已成为普通 AI 页默认调用路径；Electron smoke 覆盖 sidecar 启动、ModelProxy no-key fail-closed、结构化结果缺失和 SQLite readback。
- 本机没有 `DEEPSEEK_API_KEY`，因此只记录本地边界通过；不得将 no-key 失败误报为 live provider 成功。

### 证据映射规则（2026-08-11）

- sidecar 事件已经是运行时事实：成功 console 的 `toolRuns` 从 `tool_call/observe` 折叠，`sources` 从结构化 evidence 生成；不能用旧的关键词推断替代这些字段。
- 由于当前机器没有 live completion，这一映射只完成了类型和持久化边界，尚未证明真实模型能稳定返回合法 evidence 或触发真实业务工具。

### 工具成功状态与并发适配（2026-08-11）

- HostToolProxy 契约的三态是 `used/blocked/failed`；不能把上游通用的 `succeeded` 状态名直接套进宿主结果，否则真实允许工具会被 AgentLoop 当作失败。
- DeepTutor DeepSolve/Mastery 的旧模块通过全局符号解析 `AgenticChatPipeline`；宿主注入模型时必须保护替换/恢复窗口，否则并发回合会互相覆盖并永久停在 running。

### 可暂停工具的工程教训（2026-08-11）

- sidecar 的异步 `user_input_request` 不能只停留在日志：必须由 main 建立 durable checkpoint，再把 request 事件通知 renderer；否则 UI 无法知道 AgentLoop 正在等待什么。
- 事件序列不能使用并发的 `MAX(sequence)+1`：HostTool、checkpoint 和 sidecar stage 可能同时写入同一个 run，必须按 run 串行分配宿主 sequence。
- 输入结果要在桥接层做 schema/status/turn 归属校验，在 main 再做业务边界校验；单层校验会留下伪造结果唤醒等待者或超长 payload 的风险。
- Electron smoke 验证了 answered 与重复提交，但没有跨进程恢复；下一轮应先定义“重启后恢复还是安全过期”的产品口径，再实现对应 readback/eval，不能把内存 Promise 当作持久化恢复。
- 取消路径也必须有终态证据：本轮 smoke 验证 `cancelled checkpoint → blocked run`，避免把用户主动停止误记为成功或永久等待。
### 2026-08-11 DeepTutor capability adapter lessons

- Upstream capabilities load their own settings; a vendored adapter needs explicit non-secret config fixtures or it fails before the pipeline starts.
- Do not build a dictionary of all capability class attributes eagerly: importing a sibling capability can throw and leave a turn without terminal evidence. Select the class conditionally with `getattr`.
- Deterministic fake completions must match the upstream stage protocol (plan/quiz/finish) so the real parser and result envelope are exercised; otherwise a smoke can pass only at transport level.
- Capability outputs need a teacher-confirmation boundary before touching Omni business tables; a successful upstream result is not permission to write.
- Research and visualization configs are capability-specific (`mode/depth` and `render_mode`); passing generic topic-only config fails validation. Visualize offline smoke must return a real renderable Mermaid code path, not JSON wrapped as Mermaid.
- Do not infer mastery from arbitrary prose. The adapter accepts explicit `knowledgePoint` + boolean `isCorrect`; a `mistake` record can only provide negative evidence, while other unstructured records are counted as unknown. This preserves the “evidence insufficient = unknown” rule.
- `mastery_status` 首次接入时 smoke 一度失败，原因不是数据库或上游能力，而是新增 descriptor 后忘记把工具加入 `router.allowedTools`；工具注册、路由 allowlist、route/context policy 三处必须同一变更验收。
- HostToolProxy 的结果事件最初只保存 status/toolName，无法在审计中证明是否泄露原始记录；现在 sidecar 仅保存 result keys 和布尔脱敏标记，测试应检查“可验证的最小证据”而不是把完整 modelResult 写入事件。
- `mastery_quiz` 不能只在 `_HostProxyTool.execute` 里自动询问：宿主显式 `hostToolRequest` 会绕过 upstream tool object，必须在 bridge 的 `_request_host_tool` 同样接入 user-input checkpoint；否则工具显示 used 但永远不暂停。
- `mastery_grade` 的写回不能信任模型携带的答案；主进程从私有 question row 读取已提交答案，做一致性校验、状态幂等和显式 JSON evidence 写入，重复评分必须 blocked。
- `mastery_build` 初版会跳过坏模块，导致“部分成功”污染路径；已改为只要任一模块/知识点非法就整体 blocked，并在 append 时由数据库重映射模块/知识点 ID，避免重复 ID 破坏后续评估。
- 取消题目时要同时收敛业务 question 状态和通用 capability checkpoint；只取消 checkpoint 会留下可被后续 tool call 重放的私有答案。
- 生产复核发现 assess/build 直接写回会绕过教师控制；修复为 pending confirmation 后再写入，并在 smoke 中验证 reject 不改变路径版本。评测用例必须验证“拒绝后无 mutation”，不能只验证 happy path。
- 进程级复核发现仅在 sidecar client 中清空 pending 不足以证明产品 run 终态；必须由 main 的 `onExit` 处理器写 SQLite failed guardrail、取消 checkpoint 并清理 run binding。恢复测试还要验证重启后新 turn 可握手，不能把“进程重启成功”当作旧 turn 自动续跑。
- 掌握策略复核发现“概念题答对”不能等同于“概念已掌握”：若不区分 quiz 与教师 assess，定性知识点会被单次小测错误晋级。现在快照显式保存 `evidenceKind`，policy 仅接受经确认的 assess 正确证据；策略测试必须同时包含 quiz 不通过与 assess 通过两个对照用例。
- E16 复核发现报告如果只把统计结果交给模型，确认项可能丢失老师指定的时间窗和来源绑定。现在 sidecar event 只回传安全的窗口/来源 ID 元数据，主进程将它写入 `AiConsoleRunResult.learningAnalytics` 并用于 confirmation payload；原始记录正文仍不进入事件。测试必须同时验证自定义日期、空数据、来源 readback 和重复确认阻断。
- E16 对抗性复核还发现通用 `boundedPayload` 原先虽然标记了 `truncated=true`，却把完整 payload 通过展开字段一并返回，导致超长工具结果仍可能泄露。现在超限结果只保留安全标量和 bounded preview；新增的 tool-calling smoke 必须验证 preview 长度和不存在完整 payload，而不是只检查截断标记。
- 旧版 `runAiAgentLoop` 仍可能承接学情工具调用；报告元数据不能只绑定 DeepTutor console 事件。现在 DeepSeek 旧入口也透传 `learningAnalytics` 的窗口、subject 和 sourceRecordIds，确保两条入口的 confirmation payload 语义一致。
- E14 首轮 smoke 暴露了重算指纹泄露风险：如果把原始 `content/title` 直接序列化到 `recalculationKey`，即使分类正文已过滤，模型结果仍会携带敏感文本。现在改用本地稳定 fingerprint，只返回不可逆的 bounded 元数据；新增 E14 对抗用例必须检查私密正文不出现在任何结果字段。
- E17 对抗性复核发现：即使命令本身被判定为非法，如果把原始非法字符串放入 `commands[].command`，仍可能成为隐私/提示注入旁路。现已对拒绝命令统一替换为 `[已拒绝命令]`，只保留 bounded warning；smoke 必须同时检查原图路径、OCR 隐私、恶意命令和拒绝文本不出结果。
- C01 对抗性复核确认：仅有 `version` 字段而不在 SQL `WHERE` 中匹配会形成“最后写入覆盖”；当前更新语句同时校验 `status/deleted_at` 与版本，冲突返回明确错误。删除后的记录仍保留用于恢复/审计，默认查询才隐藏。
- C02 对抗性复核发现：仅限制 `output` 正文仍可能从 notebook 标题、摘要、用户问题或查询参数泄露教师隐私；现改为对所有模型可见文本统一调用 `sanitizeProblemText`，并在工具边界对 notebookId/recordId 做本地范围校验。另一个陷阱是“按需”只写在 prompt 里却仍把工具放进静态 allowlist；当前 router 明确检测 notebook 触发词后才添加 `teacher_notebook`，普通 general_qa 不带该工具。专项 smoke 必须覆盖敏感信息、长度预算、跨备课本、缺失记录、HostTool round-trip 和 no-write。
- C03 对抗性复核发现：把 Question Notebook 直接叠加到 `practice_design` 的默认 policy 会把学生档案、学习记录、教师资料和相似题工具一起暴露，产生不必要的上下文读取；现按任务意图把 context 收敛为仅 `question_notebook`。另一个风险是把题目收藏当成第二题库，造成题干/答案漂移；当前所有收藏/分类/usage 都只保存题目 ID 与 overlay 元数据，题目正文始终回读 `question_bank_items`。专项 smoke 必须覆盖 stale version、分类删除恢复、重复 usage、未知题目、敏感题干脱敏和 no-duplicate-corpus。

- 最终 JSON 截断复盘（2026-08-12）：解析失败不一定来自模型。`mapDeepTutorEvent` 把 `result` 当普通 trace 截到 8,000 字符，会把合法 JSON 人为变成截断 JSON；应在 provider envelope→sidecar event→main persistence→parser 每一跳检查长度与尾部。正确做法是区分 8,000 字符轨迹摘要和 64,000 字符最终结果，同时保留硬上限和长 JSON 回归。
- 测试命令复盘（2026-08-12）：PowerShell 用分号连续执行命令时，后一个成功会掩盖前一个失败退出码。本轮首次长 JSON 断言因模板内正则转义失败但后续 build 成功；随后改为 `endsWith` 并单独重跑测试。关键验收应逐条运行或显式检查 `$LASTEXITCODE`。
- 前端反向审计复盘（2026-08-12）：以 preload API 名称对 renderer/Electron smoke 做引用计数，能发现“后端已实现但没有用户入口”的真实空白。本轮先补教师备课本，因为 CRUD、版本锁和软删除均已存在；没有 record restore IPC 时只能显示审计状态，不能在 UI 承诺恢复。

## 2026-08-12 结构化结果二次截断复盘

- 只修 Electron `mapDeepTutorEvent` 的 8,000 字符上限仍不够；完整链路还必须检查 AgentLoop 请求预算和 Python sidecar 发出事件前的切片。本轮同一合法 JSON 在 provider 模拟响应中为 27,314 字符，经过 sidecar 后只剩 20,000 字符，证明错误发生在 parser 之前。

## 2026-08-12 JSON repair 二次截断复盘

- 只提高初始/最终模型回合预算还不够；repair 是独立 provider 请求，若不显式传 `max_tokens`，会重新落回 provider 默认值并再次截断长 JSON。
- 同一结构化协议不应在不同入口维护不同修复次数和请求参数。抽成共享请求函数后，测试可以直接断言 8,000 tokens、零温度、JSON mode 和无 tools，而不是只从注释推断。
- 两次 repair 是有界恢复，不是放宽 schema。每次失败原因进入可见 guardrail trace；两次仍失败继续把 run 结算为 failed。模拟与 Electron 回归通过不能替代真实 Key 的 provider live gate。

## 2026-08-12 JSON-ish 完整对象复盘

- JSON mode、足够输出预算和 provider repair 都不能保证第三方模型一定返回严格 JSON；如果 parser 仍只有 `JSON.parse`，完整但含尾逗号或裸换行的对象会被误判成完全没有 JSON。
- 正确边界不是“尽量修任何文本”，而是只修有界、首尾完整的对象外壳，再执行原有全部语义校验。这样修的是语法，不是事实、route 或确认字段；截断 JSON仍失败关闭。
- 回归应先证明修复前样本失败，再覆盖尾逗号、字符串裸换行、代码围栏、解释文字、长结果和截断拒绝。只测试合法 `JSON.stringify` 样本无法发现线上 JSON-ish 漂移。
- 并发执行多个门禁时，某个 `npm audit`/测试非零可能让编排工具只返回最后一个错误；需要独立捕获每项结果。npm 镜像不一定实现 audit API，审计失败要区分“端点不支持”和“发现漏洞”。

## 2026-08-12 完整数据备份前端验收复盘

## 2026-08-12 AI 对话库验收复盘

- “文档产物能挂到某个对话”不等于对话库本身可用。此前 E2E 直接创建 session/append message，只证明 DB API；只有从新建文件夹、右键重命名、拖放移动和归档确认开始，才能发现真实侧栏交互问题。

# 2026-08-12：JSON 模式成功响应不等于可解析回复

- DeepSeek 官方说明 JSON Output 仍可能返回空 `content`，`finish_reason=length` 也会留下截断对象；只检查 HTTP 200 或 choices 存在会把供应商边界问题拖到最终 Schema 层，形成无意义的“模型没有返回合法 JSON”。
- 正确恢复点是持有凭证与 provider 响应的 Electron main：先检查 `finish_reason/content`，只重试一次，再让同一套本地 Schema fail-closed；不能在 renderer 猜测或把纯文本包装成成功 JSON。
- 可观测性只需记录终止原因和恢复状态，不需要保存原始 prompt、隐式推理或完整失败输出。

## 2026-08-12 本地复盘报告前端验收复盘

- 旧文案“老师确认后保存”不符合现有实现：教师点击生成时，`generateReview()` 已经写入 SQLite 和 Markdown。确认队列约束的是模型发起的写入，不应套到教师主动生成；验收前必须先追清副作用发生点。

## 2026-08-12 DeepTutor 控制台无输出复盘

- 症状：界面显示调用了工具但没有答案，或长时间后返回空内容。
- 根因：控制台把所有任务都发给 `chat` capability，而宿主 route allowlist 没有允许 `chat` 处理 `student_diagnosis`；工具全部 blocked 后模型退化为 `ask_user`。同步入口没有把等待输入状态作为可交互结果返回，继续等待到 120 秒超时。
- 证据：临时 Electron run 的事件顺序为 `resolve_student_reference blocked`、`load_tools blocked`、模型再次请求 `ask_user`、`waiting_input`，最终 `DeepTutor turn timeout`；同一 run 的最终 `contentLength=0` 且 schema 报“未返回最终回复”。
- 另外，DeepSeek v4-flash 在较低 `max_tokens` 下可能出现 reasoning 消耗完预算、`finish_reason=length` 与空 content；已有 JSON recovery 只覆盖无工具最终轮，不能替代 route/等待输入链路修复。
- 改进：任何 AI acceptance 必须覆盖当前可见入口、每个主要 route、工具审核结果、`waiting_input`、timeout 和最终 content/schema；不能用旧 `runDeepSeek` 或低层 sidecar smoke 代替当前控制台验收。

## 2026-08-12 Agent Harness 打通复盘

- route 与 capability 是两层概念；如果控制台固定 `chat`，即使 router 正确，宿主权限仍会把学生诊断工具全部拒绝。映射必须由控制台和 HostToolProxy 共用同一模块。
- 工具调用状态不能按单次请求重建。学生名解析是前置工具产生的运行状态，若不保留，下一工具会再次认为“没有学生”，造成无效 `ask_user` 循环。
- `waiting_input` 不是最终回答。同步 IPC 需要在 renderer 的输入卡片提交后继续等待同一 AgentLoop；仅把状态写入 SQLite 仍会让前端收到空 content。
- Live 验收先暴露了两个与模型无关的故障：旧库迁移在新增列前创建索引，以及从构建入口启动时 Python 模块根路径计算错误。只跑全新临时库和低层 bridge smoke 会漏掉这类真实用户环境问题。
- Sidecar 吞掉 stderr 会把可诊断错误降级成无意义的 exit code；正确做法是只在失败时返回凭证脱敏、长度受限的诊断尾部。
- TRAE 的启发不是复制系统 Prompt，而是把身份、协作、上下文、工具权限、文件安全和交付证据拆成可版本化控制面，再用真实 trace/eval 验收。
- 长链 Electron smoke 的单次 UI locator 超时不能直接归因于当前改动；保留首次失败证据并原样重跑，若重跑 207/207 通过则按时序波动报告，不能隐去失败或伪称首次即通过。

## 2026-08-30 小智轻量化复盘

- 体感差不一定来自模型能力，所有请求无条件经过 route、capability、sidecar、schema repair 和 grader 本身就是成本。普通问答应先绕开不适用的控制面，而不是再叠加分类模型。
- fast path 必须保守且可回滚。学生语义不能只识别“学生/小A”，还要覆盖“这个孩子、他最近”；同时中文“小X”规则会把“小数”误判为姓名，边界样例必须包含语序与标点变化。
- direct 的后端轻量化若不同时修改等待/完成文案和旧事件清理，用户仍会看到“正在组织上下文/完成 AgentLoop”，体感不会真正变轻。
- `schemaValid=false` 与 `schemaApplicable=false` 含义不同。运行时联合契约和 SQLite 审计必须同时保存适用性，否则后续质量分析会把无需校验的 direct 请求当成失败。
- 本轮 Sol 首次规划和 Luna 首次实施都出现未及时收敛；缩小任务、限定工具调用并由独立 Sol 逐轮验收后才闭环。子 Agent 自报完成不能替代主线程复验。

## 2026-09-16 最终方案文档复盘

- 旧方案把个人桌面产品、团队云协作和千万级平台混在同一演进叙事中，容易让后续 AI 继续堆后端。最终方案应先固定唯一产品中心、数据真源和上市否决项，再允许模块实现。
- OCR 不能只写“使用 PaddleOCR”。普通中文批量识别与公式/复杂版面的资源需求不同；采用 RapidOCR 默认路径和 PaddleOCR 增强路径，才能兼顾普通 Windows CPU、安装体积和教育资料公式能力。
- 30–40GB 不是一句容量指标，而是增量扫描、幂等任务、断点恢复、索引可重建、源文件变更检测和 UI 不冻结的一组系统约束。
- “模块完成”必须绑定前端入口、错误态、数据 readback、重启和 E2E。否则会再次出现后端已经堆积而教师无法真正操作的问题。

## 2026-09-16 大规模修改约束复盘

- 根 `AGENTS.md` 比深层方案文档更容易被下一轮代理优先读取；如果其中仍保留 Vue、旧 MVP 阶段和不存在的 docs 01–09，即使最终方案正确，执行仍会被旧约束带偏。
- 大规模修改不能等同于大爆炸重写。对已经有大量后端、IPC 和测试的项目，安全做法是先冻结能力矩阵和迁移合同，再逐个贯通纵向切片。
- 拆分巨型文件本身不是用户价值。只有在本轮业务切片触及对应领域、已有测试锁定行为、旧入口仍可回退时，才应增量抽取 `App.tsx`、`db.ts` 或 `main/index.ts`。
- 旧库迁移和新库建库必须同时验证；只在空数据库通过会漏掉真实用户升级问题，只在旧库通过会漏掉建表顺序和默认值问题。
- 大改最容易重新出现“后端完成、前端和测试没跟上”。因此完成定义必须把用户按钮、失败状态、readback、重启和 Electron E2E 写进约束，而不是留给收尾阶段。

## 2026-09-24 桌面启动文档复盘

- Electron 开发模式会打印 renderer 的 localhost 地址，但真实功能入口是随后启动的 Electron 窗口；只访问 localhost 会绕开主进程、preload、SQLite、文件系统和 sidecar，不能用于功能验收。
- Python sidecar 由 Electron main 按需启动，不需要用户再开一个长期 Python 终端；但应显式设置 `OMNI_EDU_PYTHON`，避免 Windows 多 Python 环境被硬编码候选或 `py -3` 选择错误版本。
- 人工测试应设置隔离 `OMNI_EDU_DATA_ROOT`，但不能设置 E2E dialog adapter 变量，否则原生文件对话框会被测试桩替代，形成错误的人工验收结论。
- “窗口成功出现”只证明启动链路；完整功能仍需 `test:smoke` 的真实用户动作、SQLite/文件 readback 和重启断言。

## 2026-09-24 Harness 重做首切片教训

- 旧错题页面虽然显示“脱敏预览”，发送提示仍拼接了学生显示名；隐私边界必须检查最终 IPC/模型输入，不能只看 UI 文案。
- 当前 `ai_agent_runs/events` 能记录运行与终态，但不等于 LangGraph 节点 checkpoint。图的重启恢复尚需单独落地与旧库副本验证。
- 新图可先复用现有主进程工具审核与质量门禁；测试要覆盖模型失败、schema 失败及实际 Electron 点击，单独 build 不能证明用户闭环。
- Electron smoke 若继承本机 `.env.local` 的模型密钥，会把原本的无凭证失败测试变成真实网络请求。隔离测试必须屏蔽本机凭证并保留测试专用数据根，才能稳定验证失败态且避免意外外发。
- React 数组可为空但仍为 truthy；`similarQuestions: []` 会吞掉待确认题组的 fallback，模型成功却无教师可编辑预览。应先检查数组长度并以已持久化的确认载荷为预览真源。
- 教师预览编辑若只存组件 state，而确认从数据库读取原载荷，会导致 UI 与实际产物不一致。确认 IPC 必须携带受限编辑字段，主进程校验后回读正式产物。
- provider 连接在 TLS 握手前复位时，`fetch failed` 不能被解读为凭证错误或模型质量失败；应分别验证本机直连、代理与 HTTP 响应边界，并保持确定性实例验收与真实 provider 验收分开记录。
- 聊天页原来外套 92px 全局导航和工作台卡片，即使内部有会话侧栏也无法呈现桌面三栏阅读体验。AI 路由可使用独立全窗布局，但必须给真实返回工作台操作，并让 E2E 从当前可见入口导航。
- 页面右侧“本轮状态”不能只依赖当前组件内存：打开旧会话会清空 `aiResult`。应回读助手消息已保存的运行、来源和工具摘要，并明确区分空白与失败。
- 复用的 PromptInput.Send 已在 `onPress` 调用上层 `onSubmit`；额外绑定 `onClick` 会产生第二条提交路径。受控输入应在发送被接受时立即清空，不能等异步创建会话后才清空。
- 主进程网关、sidecar 事件、IPC 拒绝与历史消息都可能携带连接失败文本；用户可见的 AI 错误应在最终结果和界面边界再归一化，但仍需把 TLS 不通与密钥无效分开。
- Electron 全量 smoke 中讲义区块持久化已回读，但预览 DOM 尚未刷新就立即断言会偶发失败；等待预览文本实际更新后再断言，才能测试最终 UI 状态。
- 新供应商不能只切设置页：direct、DeepTutor ModelProxy、JSON 修复、旧 structured 和 LangGraph 题组都必须传递 provider；否则后续模型回合会悄悄回到默认 DeepSeek。
- 智谱截图中的 `/api/anthropic` 属于 Claude 协议；小智当前请求与工具回合使用 Chat Completions，需走官方 `/api/paas/v4/chat/completions`。用无效隔离密钥收到 GLM 鉴权错误，只证明路由和连接，不证明有效密钥或生成质量。
- Claude Code 映射页的 Sonnet/Opus/Fable/Haiku 是角色标签，应读取“实际请求模型”列作为 GLM API 模型 ID；页面的 1M 勾选不等于小智已具备对应上下文。Coding Plan 接入与标准模型 API 的密钥可用性须分开验收。
- GLM 标准接口和普通/structured 页面回复成功也不能证明教师题组图通过：真实模型曾把 role、difficulty 输出为中文，严格 schema 正确阻断待确认写入。图应明确枚举并只允许一次带原错误的受控修复，修复后仍做来源与教学门禁。
- 真实三题 JSON 输出可能超过 45 秒；超时必须是失败终态、零业务写入，且任务图可以用独立有界预算。将图模型上限调到 90 秒后，真实生成、确认和重启读回已通过；不能把一次成功当作延迟稳定性证明。
- LangGraph 默认会把每个 State 字段连同 pending writes 存入 saver；不能把含完整 Student/records 的 `CompiledAiContext` 直接放入图状态后再持久化。先收窄到脱敏有界载荷与来源 ID，并检查 checkpoint、metadata、pending writes 三处 blob。
- Electron 的 `store.init()` 在 main 启动和 renderer bootstrap 均会调用；重启遗留 run 的回收只能对 Store 实例执行一次，否则会把当前运行误标为中断。
- E2E 若仅从 `listAiAgentRuns` 的最近 N 条按“不等于前一 ID”找新 run，会在并发/时间戳并列时误选旧 run。助手消息携带的 run ID 是教师看到的结果与 SQLite 运行记录之间更直接的关联证据。
