# 小智状态写锁恢复合同

## 问题证据

`daily-0AxcRF` 在首个 `office_list_attachments` 工具准入时，HTTP 200 已经产生，但事件回执没有在 15 秒内完成，最终以 `event_persistence` 终止。运行记录仍保留用户消息、助手说明和排队中的工具尝试，事件日志游标停在失败前，说明模型与工具没有继续越过未持久化门槛。

当时的写入连接使用 `BEGIN IMMEDIATE` 和 `busy_timeout=5000`。同一小智状态写入虽然已经排队，但其他 Store 写入仍可能短暂持有 SQLite 写锁；每个排队连接在锁冲突时同步等待 5 秒，多个连接会让 libuv 工作线程被长期占用，形成“等待能力本身被等待耗尽”的放大效应。

## 第一性目标

1. 公开事件和工具准入回执仍是执行前的强制持久化门槛，任何模型或工具副作用都不能越过未提交记录。
2. 短暂写锁冲突应通过异步退避恢复，不占用 libuv 工作线程，不让单个慢事务拖垮整个状态链。
3. 锁持续存在超过可恢复窗口时，仍明确失败并停止本轮，不能伪造成功、跳过回执或无限重试。
4. 原 `daily-0AxcRF` 及其失败证据保留，不用后续偶然成功覆盖。

## 冻结范围

- 只调整 `OmniEduStore` 为 `xiaozhiState.sql.transaction` 创建写事务时的锁获取策略。
- `BEGIN IMMEDIATE` 因 `SQLITE_BUSY` 或 `SQLITE_LOCKED` 失败时立即关闭该连接，异步退避后重试获取锁。
- 事务动作一旦开始执行，锁冲突重试不再覆盖或重放动作。
- 重试总窗口必须短于生产 15 秒关键持久化门禁，并保留明确的最终失败。
- 不新增表、IPC、依赖、Agent Loop，不改变事件 schema、教师确认、文件权限、隐私或 provider。

## 验收标准

1. 生产 Store 的普通状态写、事务回滚和冷读原 4 项继续通过。
2. 新增真实 SQLite 写锁反例：独立连接持有写锁 6 秒，期间两个生产状态事务尝试写入。
3. 修复前 5 秒 `busy_timeout` 会让首个排队事务失败；修复后两个事务应在锁释放后恢复并提交，不丢行、不交叉。
4. 完成后从冷 Store 读取两个事务写入的值，证明不是内存假成功。
5. 终态仍需有界：持续锁不能无限等待，代码层面的总重试窗口必须小于 15 秒关键门禁。
6. 构建、renderer 组件、状态写专项和 `git diff --check` 通过；相关 Electron 进程为 0。

## 边界

本片只证明 SQLite 短暂写锁的本机恢复。它不替代真实教师、课程质量、真实 DeepSeek 全链、VPN-off、安装包或 Office/WPS 放映验收，也不把历史 `daily-0AxcRF` 改写为通过。
