# H10 公开图片预填步骤容错合同

## 最终同构建复验

`4dfb959f3ed9e60d38f6f0313c64293bcf47441cd1fb8c1cf9f3dee2ff75ee40`/373上，`pi-public-image-ui-z19EBM`与`DnmrJ6`各自13/13。两轮都覆盖公开用途确认前零图片发送、真实DeepSeek视觉请求、教师拒绝、停止、供应商失败回执、冷恢复和双尺寸UI。

原`wGFxRF`保持失败。修复只忽略不存在任务步骤上的安全只读路由提示；已存在步骤仍正常准入，写工具、外部效果、图片用途确认、供应商送达和教师核对均未放松。

## 问题证据

`pi-public-image-ui-wGFxRF` 中，模型已经列出附件，却给`office_view_public_image`提前填写了尚未采用的`taskStepId=view_public_chart`。该工具effect为`local_cache`，本应在无任务计划时直接进入教师公开图片用途确认；错误步骤ID使它被`task_step_missing`转成`task_blocked`。随后模型多次提交`image`计划，目标又使用文件名而非附件ID，全部失败，最终没有发起确认卡。

## 第一性目标

安全读取和本地缓存不应依赖尚未存在的任务步骤。模型预填一个未采用的步骤ID时，宿主应忽略该路由提示并继续执行工具自身的权限/反写/教师确认边界；若该ID真实存在于当前任务，则仍按任务准入关联证据。错误预填不能伪造步骤进度，也不能让本地安全动作卡死。

## 冻结范围

- 只调整`tasks/plan-runtime.ts`：`safe_read`/`local_cache`带stepId时，先只读判断该step是否已采用；不存在则按无计划安全读取继续，存在才进入正常任务准入。
- `office_view_public_image`仍必须经过原有公开声明、用途确认、能力、准备、供应商送达和教师核对边界。
- 写工具、保存工具、浏览器navigate/交互及其他外部效果仍必须依赖真实任务步骤。
- 图片提示明确：没有已采用的image步骤时，`office_view_public_image`不填`taskStepId`，不先建旧`update_plan`，直接调用发起用途确认。
- 不新增表、IPC、依赖、AgentLoop或绕过教师确认。

## 验收标准

1. 任务计划边界增加反例：并发持有任务写锁时，safe/local缓存即使携带未知stepId也不等待任务写锁，仍可直接执行；写工具继续受阻。
2. 已知合法stepId的任务读取仍进入admission并关联证据，不因本修复跳过任务核验。
3. 公开图片真实Electron路径重新通过：附件→直接用途确认→教师批准→真实视觉请求→盲答案→停止/拒绝/冷启。
4. 原`wGFxRF`失败保留，不改为成功。
5. 构建、任务专项、renderer及最终同构建证据通过。

## 边界

本片只修错误预填任务步骤对安全本地缓存的阻塞，不关闭真实学生图片、VPN-off、安装、真人教师或完整H10。
