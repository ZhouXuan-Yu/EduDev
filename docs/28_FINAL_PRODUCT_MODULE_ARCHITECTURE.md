# Omni-Edu Agent 最终产品与模块架构基线

版本：v1.0  
日期：2026-09-16  
状态：后续产品与开发的最高优先级方案基线  
适用对象：产品、设计、前端、Electron 主进程、Python Worker、测试与后续 AI 开发代理

> 本文确定最终产品形态和模块边界，不是阶段性路线图。旧文档与本文冲突时，以本文为准；旧文档中的“已完成”仍必须用当前代码、真实界面和测试证据重新核验。

## 1. 最终产品定义

Omni-Edu Agent 是面向 K-12 独立教师、辅导老师和小微教研团队的本地优先桌面软件。它把教师散落在电脑中的 30–40GB 讲义、试卷、题库、解析、图片和学生错题，整理成可检索、可追溯、可持续积累的个人教学资产，并完成两条核心闭环：

```text
教师资料 -> 解析与索引 -> 题库/知识库 -> 按蓝图组卷 -> 教师确认 -> 试卷与解析
学生错题照片 -> 本地 OCR -> 教师校正 -> 错因/知识点 -> 相似或变式题 -> 针对性练习
```

它不做学校级教务系统、学生端、家长端、完整 LMS、多租户平台或自动教学决策系统。“小智”是跨模块助手，不是产品中心；知识资产、题库、组卷和错题训练才是产品中心。

### 1.1 核心用户

- 主用户：拥有长期资料积累、需要频繁备课和出卷的 K-12 教师。
- 次用户：2–30 人的小微教研团队，但单机教师体验优先。
- 非目标用户：学校管理人员、家长、学生自助学习用户和大型教务平台运营者。

### 1.2 解决的问题

- 资料很多但无法统一搜索、复用和追溯。
- 手工找题、改题、排卷和写解析耗时。
- 学生错题照片无法稳定转为结构化、可训练的数据。
- 通用大模型不知道教师自己的教材范围、出题偏好和历史题库。
- AI 生成内容来源不清、质量不可控，教师不敢直接使用。

### 1.3 商业价值与护城河

产品具备实际付费价值的前提不是“能聊天”，而是能长期节省教师整理资料、找题、出卷和针对性训练的时间。护城河来自以下复合资产：

1. 教师经过确认的私有题库、解析、标签、难度和使用反馈。
2. 原题、改编题、AI 生成题之间完整的来源谱系。
3. 学生错题、知识点、错因、训练结果形成的长期闭环。
4. 组卷蓝图、教师修改记录和最终采用结果形成的偏好数据。
5. 30–40GB 本地资料可离线处理、可备份、可迁移带来的信任。

## 2. 不可改变的产品原则

1. **本地优先**：原始资料、学生档案、错题图片、题库和索引默认保存在本机。
2. **脱敏上云**：云模型只接收完成脱敏的必要文本和摘要，原图和整库不自动上传。
3. **教师最终确认**：OCR、知识点、答案、解析、改编题和整套试卷都必须可编辑、可拒绝、可确认。
4. **来源可追溯**：每道题必须能说明来自哪份资料、哪一页、是否改编、由谁确认。
5. **大文件不进 SQLite**：SQLite 保存结构化事实和文件元数据，原文件、预览图、题图和导出物放文件系统。
6. **索引可重建**：全文索引、向量索引、缩略图和缓存不是业务真源，损坏后可从 SQLite 与文件重建。
7. **模块完成必须贯通界面**：后端实现不等于完成；必须同时有 typed preload、可操作前端、失败状态和真实 Electron E2E。
8. **不以 AI 代替确定性规则**：权限、隐私、数据校验、来源、分值、答案完整性和发布门禁由本地规则控制。

## 4. 总体架构与数据真源

```text
React Renderer
  | 仅调用 window.omniEdu typed API
Electron Preload
  | IPC schema + 参数校验
Electron Main
  |-- SQLite：业务真源、任务、审计、来源谱系
  |-- Local File Store：原文件、题图、预览、导出、备份
  |-- Python Worker：解析、OCR、切题、embedding、向量检索
  |-- AI Gateway：脱敏后的分析、改编和生成
  `-- Export Engine：DOCX / PDF / Markdown

Derived Indexes
  |-- SQLite FTS5：关键词和精确文本检索
  `-- LanceDB：本地向量检索，可删除后重建
```

### 4.1 技术选型总表

| 能力 | 最终选择 | 选择原因 | 不采用为默认方案的技术 |
| --- | --- | --- | --- |
| 桌面端 | Electron + React + TypeScript + Vite | 与现有项目一致，适合本地文件、SQLite 和离线工作流 | 不重写为纯 Web 或另一套桌面框架 |
| 主业务库 | SQLite WAL | 单机事务可靠、可迁移、运维成本低 | Redis、向量库不能做业务真源 |
| 文件存储 | 版本化本地数据目录 | 适合 30–40GB 原始资料和可恢复备份 | 不把 BLOB 塞进 SQLite |
| 文档解析 | Docling 为统一解析层 | 覆盖 PDF、Office、Markdown、HTML、图片并可输出结构化 JSON/Markdown/chunks | 不为每种格式自建一套解析器 |
| 普通中文 OCR | RapidOCR 2.x + ONNX Runtime CPU | Windows 本地部署轻、PP-OCR 中文模型成熟、适合大量普通文字页 | Tesseract 不作为中文教育资料默认引擎 |
| 公式/复杂版面 OCR | PaddleOCR 3.x PP-StructureV3 + PP-FormulaNet | 提供版面、表格、公式与阅读顺序能力 | 不让通用多模态云模型直接处理整库原图 |
| 图像预处理 | OpenCV | 旋转、透视、去阴影、裁剪、清晰度检测成熟 | 不把预处理逻辑散落在前端 |
| 关键词检索 | SQLite FTS5，中文正文优先 trigram | 与业务库同进程、可解释、可离线 | 首版不引入 Elasticsearch/OpenSearch |
| 向量检索 | LanceDB embedded | 可指向本地目录，适合桌面内嵌和可重建索引 | 不在单机版引入独立 Milvus/Qdrant 服务 |
| 默认 embedding | `BAAI/bge-small-zh-v1.5` 的本地 ONNX 版本 | 中文效果与 CPU 资源占用较平衡 | `bge-m3` 仅作为高质量可选模式，不强制所有电脑运行 |
| AI Provider | 现有 DeepSeek Adapter + 可替换 provider 接口 | 保留现有结构化回复、grader、审计和降级能力 | 业务模块不得直接调用供应商 SDK |
| DOCX | `docx` npm 库 + 固定模板 | 可生成可编辑 Word 产物 | 不继续扩大手写 ZIP/XML 实现 |
| PDF | Electron/Chromium HTML print-to-PDF | 复用现有 Chromium，中文字体和分页可控 | 不以简单 PDF 字节拼装承担复杂排版 |
| Python 分发 | 独立 Worker + PyInstaller one-folder + 外置版本化模型目录 | 用户不需安装 Python，模型可独立更新 | 不要求教师配置 Conda/系统 Python |
| Windows 安装 | electron-builder + NSIS + 代码签名 | 安装、卸载、数据目录保留和升级生态成熟 | 开发态 `npm run dev` 不能当交付方式 |

技术依据：Docling 官方列出的输入覆盖包括 PDF、DOCX/XLSX/PPTX、图片和 Markdown，并支持 JSON、Markdown 和 chunks 输出；其 OCR 接口原生支持 RapidOCR。PaddleOCR 的 PP-StructureV3 面向版面、表格、公式和阅读顺序，公式管线可输出 LaTeX。LanceDB 支持本地目录形式的嵌入式运行；SQLite FTS5 提供全文查询、BM25、前缀和 trigram tokenizer。参见文末官方资料。

## 5. 模块依赖关系

这不是开发阶段划分，而是不可绕过的依赖关系：

```text
M01 本地数据底座
  -> M02 资料导入与解析
      -> M03 OCR 与切题
          -> M04 知识库与混合检索
              -> M05 结构化题库
                  -> M06 智能组卷
M03 + M04 + M05 + M08 学生档案
  -> M07 错题训练
M06 + M07 -> M09 产物与导出
全部模块 -> M10 AI 编排与治理
全部数据 -> M11 备份恢复与迁移
全部用户路径 -> M12 安装、更新、观测与测试
```

任何模块只有在“主进程/Worker → preload → 前端 → 用户操作 → SQLite/文件 readback → 重启后仍成立 → E2E”全部打通后，才允许标记完成。

## 6. 模块开发方案

### M01 本地数据底座与任务系统

**目标**：支撑 30–40GB 资料的增量扫描、断点恢复、失败重试和审计，不阻塞界面。

**开发方案**：

- 文件系统保存 `sources/`、`managed/`、`previews/`、`question-images/`、`exports/`、`indexes/`、`models/` 和 `backups/`。
- 导入支持“挂载模式”和“受管模式”。挂载模式只记录原路径；受管模式复制到数据根目录。
- SQLite 新增/统一 `assets`、`asset_versions`、`jobs`、`job_events`、`audit_events`、`schema_migrations`。
- 每个文件记录绝对路径、规范化路径、大小、mtime、SHA-256、导入方式、解析版本和状态。
- 任务状态固定为 `discovered -> hashing -> parsing -> needs_ocr -> extracting_questions -> indexing_text -> indexing_vectors -> ready`，失败进入带错误码的 `failed`，可从安全检查点重试。

**成熟技术**：Node `worker_threads`/子进程、SQLite WAL、分批事务、SHA-256、文件系统 watcher 仅作提示，定期扫描作为真正确认机制。

**注意事项**：

- 不一次性读取大文件进内存；流式 hash、分页解析、分批提交。
- 原文件删除、移动或修改后不能静默丢失，必须显示 `missing/changed`。
- 任务必须幂等；同一 hash + parser version 不重复解析。
- UI 关闭或 Worker 崩溃后，任务必须能恢复，不能永远停在 `running`。

**验收**：30–40GB 样例目录可暂停、恢复、取消；重复扫描不产生重复资源；坏文件不拖死队列；导入期间主窗口可操作。

### M02 资料导入与文档解析

**目标**：把 PDF、DOCX、PPTX、XLSX、Markdown、TXT 和图片转换为保留页码与版面来源的统一文档结构。

**开发方案**：

- Docling 作为统一解析适配层，输出 `Document -> Page -> Block -> Span`。
- 可复制文本的 PDF 先走原生文本层；扫描页才进入 OCR，避免重复识别和浪费算力。
- Office 文件保留页/幻灯片/工作表位置；旧版 DOC/XLS/PPT 通过可选 LibreOffice headless 转换。
- 解析结果保存为版本化 JSON，正文切片进入 SQLite，原始结果文件放 `derived/`。
- 每个 block 保存页码、bbox、block type、父标题、字符范围和 parser version。

**成熟技术**：Docling、pypdfium2/Docling PDF backend、LibreOffice headless 仅用于旧格式兼容。

**注意事项**：

- 解析器升级必须生成新版本，不能覆盖教师已确认的题目。
- 加密 PDF、损坏 Office、超大工作簿和字体缺失必须有明确错误。
- 第一版不承诺像素级还原复杂 Word/PDF；目标是可检索、可定位、可抽题。

**验收**：每种支持格式都有真实文件 fixture；解析后点击搜索结果能回到源文件页/块；重跑不会破坏确认数据。

### M03 本地 OCR、公式识别与题目切分

**目标**：把学生错题照片和扫描资料转成可校正的题目文本、公式、版面和题目区域。

**最终 OCR 选择**：

- 默认路径：`OpenCV -> RapidOCR 2.x -> 文字行与置信度`。适合 Windows CPU 上的大量中文普通文本，安装和运行成本最低。
- 增强路径：检测到公式密集、表格、双栏或复杂扫描页时，切换到 `PaddleOCR PP-StructureV3`；公式区域使用 `PP-FormulaNet` 输出 LaTeX。
- Docling 负责文档编排和 OCR 调度，不替代 OCR 模型本身。

**开发方案**：

- 前处理包括清晰度检测、方向分类、透视矫正、去阴影、裁边和分辨率规范化。
- 先识别整页版面，再进行题号检测和多题切分；每道题保存 crop 图、bbox 和源图坐标。
- OCR 返回文字、公式 LaTeX、行框、置信度、引擎、模型版本和耗时。
- 低置信度文字、答案区域和公式高亮显示；教师可以对照原图逐块修正。
- 教师修正保存为新 revision，原始 OCR 结果只读保留。

**注意事项**：

- 不把 OCR 置信度当正确率；低置信度必须提示，高置信度也允许修正。
- 手写字、几何图、化学式和复杂竖式不能承诺全自动正确，必须保留原图区域。
- OCR 模型与应用分开版本化；模型升级要跑固定评测集，不能直接替换。
- 原始学生照片永不自动发给云模型。

**验收**：建立至少 300 张代表性样本，覆盖手机倾斜、阴影、多题、公式、表格和手写批注；统计文字字符准确率、题目切分 F1、公式可用率、教师平均修改字符数、CPU P50/P95 延迟和失败率。没有这组数据，不得宣称“本地 OCR 已可商用”。

### M04 知识库、切片与混合检索

**目标**：让教师从 30–40GB 资料中按学科、年级、教材、知识点和自然语言找到可定位的内容与题目。

**开发方案**：

- SQLite 保存资源、页面、块、切片、标签、来源和确认状态。
- FTS5 保存可解释关键词索引；中文正文默认评估 trigram tokenizer，查询必须转义并限制长度。
- LanceDB 保存 chunk/question embedding、模型版本和 SQLite entity id，不保存唯一业务事实。
- 混合排序：结构化过滤 + FTS/BM25 + 向量相似度 + 内容质量 + 教师偏好 + 去重与多样性。
- 搜索结果必须显示来源文件、页码、命中片段、匹配原因和索引版本。

**成熟技术**：SQLite FTS5、LanceDB embedded、`bge-small-zh-v1.5` ONNX；高性能电脑可选 `bge-m3`，但必须使用独立索引版本。

**注意事项**：

- embedding 改版需创建新索引，不允许新旧向量混用。
- 先过滤学科/年级/教材，再做语义召回，避免“语义像但教学范围错”。
- 索引损坏不能影响原文件和 SQLite；设置页提供全量重建与进度。

**验收**：用教师标注的查询—相关结果集评估 Recall@10、MRR、无结果率和错年级率；搜索结果点击可回源；断电/取消后可继续索引。

### M05 结构化题库与来源谱系

**目标**：形成可检索、可编辑、可版本化、可复用的 canonical 题目库。

**题目核心字段**：学科、年级、教材版本、学期、知识点、题型、难度、题干、选项、答案、解析、分值、来源文件/页码/题号/截图、标签、使用历史、版权备注和教师确认状态。

**来源类型固定为**：

- `library_original`：教师资料原题。
- `library_adapted`：从资料原题改编。
- `ai_generated`：AI 独立生成。
- `teacher_created`：教师手工创建。

改编题必须保存 `parent_question_id`、改编说明、模型/提示版本和确认人；任何编辑都创建 revision，不直接抹掉历史。

**成熟技术**：SQLite 关系表 + JSON Schema/Zod 契约；图片和富媒体引用本地文件 id；相似题去重采用规范化文本 hash + embedding 近邻双重检查。

**注意事项**：

- “知识点”和“难度”由 AI 建议、教师确认，不可自动写成永久事实。
- 删除默认软删除；已被试卷引用的题目不能物理删除。
- 答案和解析缺失的题不能进入正式出卷池，除非蓝图明确允许并提示。

**验收**：录入、OCR 转题、批量导入、编辑、版本回退、来源跳转、去重、软删除、收藏和使用历史均有 UI 与 E2E。

### M06 智能组卷与试卷编辑器

**目标**：根据教学目标从教师资料库、改编题和 AI 生成题中产出可直接编辑和导出的试卷与解析。

**组卷蓝图字段**：学科、年级、教材、范围、知识点权重、题型与数量、难度分布、时长、总分、来源比例、近期用题排除、学生/班级、答案与解析要求。

**执行流程**：

```text
蓝图校验 -> 结构化过滤 -> 混合召回 -> 去重 -> 覆盖率/分值检查
-> 缺口分析 -> 原题改编或 AI 补题 -> 答案解析校验
-> 试卷编辑器 -> 教师确认 -> 试卷/答案/解析产物
```

**开发方案**：

- 先使用确定性算法选题，AI 只处理缺口补题、题目改编和解析草稿。
- 编辑器支持拖拽排序、换题、锁题、改分、编辑题干/答案/解析、分页预览和来源查看。
- 每次组卷保存 blueprint、candidate pool、选择理由、教师操作和最终版本。
- 校验器检查总分、题量、知识点覆盖、难度分布、重复题、答案完整性和超出教材范围。

**成熟技术**：本地检索管线、Zod/JSON Schema、React 拖拽库、版本化 HTML/CSS 打印模板。

**注意事项**：

- AI 生成题默认标记“待复核”，未确认不能导出为正式教师产物。
- 禁止只返回一段 Markdown 冒充组卷完成；必须落为可编辑结构和持久化版本。
- “按几年级改题”必须同时受教材、知识点、题型和难度约束。

**验收**：教师可从空蓝图到导出完成全流程；关闭重开后继续编辑；无网时仍可用本地题组卷；来源、分值和答案校验可见。

### M07 错题训练闭环

**目标**：从一张或一组学生错题照片生成针对性练习，并保留教师判断和训练反馈。

**开发方案**：

```text
导入照片 -> 图像质量检查 -> OCR/多题切分 -> 教师校正
-> 本地脱敏 -> 知识点/错因建议 -> 教师确认
-> 本地相似题召回 -> 变式/补题 -> 三元题组
-> 教师编辑确认 -> 导出/分配 -> 结果回录
```

三元题组固定为：原错题或等价复现题、同知识点相似题、迁移/巩固题。每道题说明“为什么被选中”，并标明来自资料库还是 AI。

**成熟技术**：M03 OCR、M04 混合检索、M05 题库、现有 DeepSeek 结构化输出和确认队列。

**注意事项**：

- 学生姓名、学校、手机号、二维码和批注中的身份信息先本地检测和遮盖。
- AI 错因只是建议；没有作答过程时不能武断判断“粗心”或能力标签。
- 当前项目已有 `needs_ocr` 和教师校正链路，但真实 OCR 引擎仍需按 M03 接入，不能把状态流当识别能力。

**验收**：真实照片从按钮导入到题组导出；覆盖取消、坏图、多题、OCR 失败、无 API Key、本地无相似题、AI 补题、确认/拒绝、SQLite readback 和重启。

### M08 学生档案与训练证据

**目标**：只保存生成针对性训练真正需要的学生信息、错题历史和反馈，不扩展成教务 CRM。

**开发方案**：学生、错题、训练集、作答结果、教师观察和知识点证据建立稳定关联；支持归档和单学生导出；所有推荐都能回到证据。

**成熟技术**：现有 SQLite 学生档案和学习记录模型，继续通过 typed preload 暴露。

**注意事项**：不保存无关敏感字段；不展示无证据的掌握百分比；学生归档后只读，训练数据仍可审计。

**验收**：学生隔离、归档、导出、错题/训练回读、重启保持和隐私字段不进入日志。

### M09 产物、排版与导出

**目标**：输出教师可真正打印、修改和交付的试卷、答案、解析与练习单。

**开发方案**：

- 统一 `artifact` 数据模型，保存类型、业务来源、版本、模板、文件路径、hash、生成状态和确认人。
- DOCX 使用 `docx` 库与固定模板；PDF 使用隐藏打印窗口加载版本化 HTML/CSS 后 print-to-PDF；Markdown 作为可审计中间格式。
- 试卷、答案和解析分离输出，也支持教师版合并输出。
- 模板管理字体、纸张、页边距、密封线、题号、页眉页脚和分页规则。

**注意事项**：公式、表格、图片、分页孤行和中文字体必须进入视觉回归；导出失败不得显示成功；文件与 SQLite hash 必须一致。

**验收**：真实 DOCX 可在 Office/WPS 编辑；PDF 打印预览无截断；双视口只是 UI 证据，还需 A4 纸面 fixture 与文件 readback。

### M10 AI 编排、质量与安全治理

**目标**：让 AI 成为可替换、可审计、受权限控制的工具，而不是业务真源。

**开发方案**：

- 保留现有 `direct | structured` 双路径和 Agent Harness；涉及学生、资料、题库、组卷、写入或风险判断一律走 structured。
- 所有结构化输出使用版本化 schema；provider 漂移时允许有限修复，但语义校验失败必须 fail-closed。
- 工具权限按页面、route 和 capability 三层限制；写入动作进入教师确认队列。
- 保存输入 hash、脱敏状态、模型/提示版本、工具事件、输出 hash、教师修改和最终采用结果。
- 无网络、无 Key、超时、限额或 provider 失败时，回退到本地搜索、确定性组卷和手工编辑。

**成熟技术**：现有 DeepSeek adapter、Zod/JSON Schema、Agent Harness、Education/Usability Grader 和 SQLite observability。

**注意事项**：deterministic proxy 不是 live model；模型评分不是教师验收；不保存隐藏推理链；不能用 AI 自动确认自己生成的题。

**验收**：真实 provider 单独标注；每条 AI 用户路径覆盖无 Key、超时、非法 JSON、越权工具、隐私拦截、确认/拒绝和降级。

### M11 备份、恢复与迁移

**目标**：让教师敢把多年资料交给软件，设备损坏或升级后可以恢复。

**开发方案**：

- 备份内容包括 SQLite、受管文件、解析版本、索引清单、模型清单、配置和 manifest。
- 默认不复制可重建向量索引以缩小备份，但记录重建所需版本；提供“完整备份”选项。
- 恢复先在临时目录验证 manifest/hash/schema，再原子切换；永不直接覆盖正在使用的数据目录。
- 提供全库恢复、单学生导出/导入和只重建索引三种操作。

**成熟技术**：SHA-256 manifest、SQLite online backup API、临时目录验证、原子 rename。

**注意事项**：当前已有备份完整性校验，但没有自动恢复；“能备份”不能替代恢复演练。

**验收**：干净机器恢复、旧版本迁移、篡改拒绝、空间不足、中断恢复和恢复后 E2E。每个正式版本都必须执行一次真实恢复演练。

### M12 安装、更新、观测与质量门禁

**目标**：从开发项目变成普通 Windows 教师可以安装、升级、诊断和卸载的软件。

**开发方案**：

- electron-builder + NSIS 生成安装包；Python Worker 与模型目录随应用分发，用户不安装 Node/Python。
- 代码签名、版本迁移、自动更新、崩溃恢复、日志脱敏、诊断包和磁盘空间预警进入正式能力。
- 自动更新只更新程序和兼容模型；用户数据目录永不随卸载/升级静默删除。
- 建立统一门禁：单元测试、契约测试、组件测试、Electron E2E、数据迁移、30–40GB 压测、OCR 基准、检索基准、导出视觉回归和恢复演练。

**注意事项**：开发态 build、smoke 和进程运行不等于可交付；Windows 原生 dialog、Office/WPS 打开、打印和升级必须在干净虚拟机验证。

**验收**：非开发电脑完成安装、首次启动、导入、OCR、组卷、导出、备份、升级和卸载；程序升级后原数据、任务和索引状态一致。

## 7. 核心数据模型

建议按下列业务域收敛现有表，而不是继续向单个 `db.ts` 堆方法：

| 业务域 | 核心实体 |
| --- | --- |
| 资料 | `assets`、`asset_versions`、`document_pages`、`document_blocks` |
| 任务 | `jobs`、`job_events`、`worker_leases` |
| OCR | `ocr_runs`、`ocr_blocks`、`ocr_revisions`、`question_crops` |
| 知识库 | `knowledge_chunks`、`chunk_tags`、`index_versions` |
| 题库 | `questions`、`question_revisions`、`question_sources`、`question_tags` |
| 组卷 | `paper_blueprints`、`paper_drafts`、`paper_items`、`paper_revisions` |
| 错题 | `mistakes`、`mistake_analyses`、`exercise_sets`、`exercise_items` |
| 学生 | `students`、`learning_records`、`practice_attempts` |
| AI | `ai_runs`、`ai_events`、`tool_runs`、`confirmations`、`quality_reviews` |
| 产物 | `artifacts`、`artifact_versions`、`export_events` |
| 运维 | `backups`、`restore_runs`、`audit_events`、`app_settings` |

所有核心实体使用稳定字符串 UUID、`created_at`、`updated_at`、版本号和软删除字段。AI 派生字段必须同时保存 `derived_by`、`model_version`、`confidence`、`confirmed_by_teacher`。

## 8. 非功能验收目标

以下是上市前必须实测的目标，不是当前已完成声明：

| 项目 | 目标 |
| --- | --- |
| 资料规模 | 单教师 30–40GB，可增量、暂停、恢复、取消和重建索引 |
| 界面响应 | 后台导入/OCR/embedding 时主线程不冻结；交互操作有明确进度 |
| 搜索 | 已建索引情况下，常用本地查询 P95 < 1 秒，并显示可追溯来源 |
| 组卷 | 任何正式试卷满足题量、总分、答案完整性、重复和来源校验 |
| 隐私 | 原图和真实身份默认不出本机；日志、诊断包和 AI 请求均脱敏 |
| 数据可靠性 | 备份可验证，恢复经过干净机器演练，升级不丢数据 |
| 可维护性 | 每个 IPC 有共享契约；数据库迁移可回放；Worker 协议有版本 |
| 测试 | 核心模块同时有失败路径、UI 用户路径、SQLite/文件 readback 与重启验证 |

## 9. 后续 AI 自动开发执行规则

后续 AI 每次只选择一个模块中的一个可独立验收切片，但必须遵守：

1. 先读取本文与四份协作文档，再检查当前脏工作树和真实实现。
2. 先列出现状证据与目标差距，不重复建设已有后端能力。
3. 同一切片同时完成共享契约、主进程/Worker、preload、前端状态、测试和文档。
4. 新增页面前先确认现有页面是否已有入口；优先补接线和真实流程。
5. 每个关键控件使用稳定 `data-testid`，但 E2E 必须从用户可见入口操作。
6. 后端 smoke 只能证明底层能力，不能替代 Electron 用户路径。
7. 报告精确测试命令、通过数量、失败与未验证边界；没有 live 证据就写“未验证”。
8. 不自动提交、推送、发布、上传数据或修改用户凭证。

### 9.1 下一次大规模修改的交付合同

下一次大规模修改不是把 M01–M12 一次性重写，而是围绕最终架构连续交付若干有依赖关系、可独立验收的纵向切片。开始前必须冻结：

- 本轮涉及的模块编号和教师可见结果。
- 现有 backend、IPC/preload、frontend、用户操作和测试证据。
- 将新增或迁移的 SQLite 表、文件目录、Worker 协议、共享类型、IPC 和页面。
- 旧数据兼容、失败恢复、功能开关或 adapter 退出条件。
- 每个切片的验收命令、数据 readback 和重启验证方式。

实施顺序遵循第 5 节依赖图。可以连续开发多个切片，但上一个切片没有真实界面和测试证据时，不得继续把依赖它的上层功能标为完成。

### 9.2 大规模修改的结构约束

- 新业务按领域拆分，禁止继续扩大 `App.tsx`、`db.ts` 和 `main/index.ts` 的职责。
- 抽取只覆盖本轮触及领域，先用现有测试锁定行为，再移动代码；不做与教师结果无关的全库重写。
- Electron main 继续作为 SQLite、文件、权限、隐私、工具审核和审计的唯一宿主；renderer 不直连 Node、SQLite、Python 或模型 provider。
- Python Worker 只处理解析、OCR、embedding 和检索等计算任务，不能绕过 main 直接写业务表。
- 任何旧入口只有在新入口完成数据回读、重启和 Electron E2E 后才可删除。

### 9.3 大规模修改的验收矩阵

| 层级 | 必须证明的内容 |
| --- | --- |
| 契约 | 共享类型、schema、Worker/IPC 版本和错误码一致 |
| 数据 | 新库与旧库迁移、幂等、失败恢复、真实 readback |
| 后端 | 主进程/Worker 处理成功、失败、取消、重试和超时 |
| 前端 | 当前导航可进入，完整状态可见，教师可编辑和确认 |
| 用户路径 | 从按钮操作到 SQLite/文件结果，不用直接 API 代替 |
| 持久化 | 关闭重开后仍可继续，索引可重建且不伤业务真源 |
| 兼容性 | 1366×768、1920×1080、Windows 路径和打包环境 |
| 真实性 | proxy、fixture、live provider、真实教师证据分别标注 |

根 `AGENTS.md` 保存完整执行和停止条件，后续 AI 必须同时遵守。

## 10. 上市否决项

任一项未完成，项目都不能宣称达到商业生产可用：

- 真实本地 OCR 未接入或没有代表性评测集。
- 30–40GB 导入无法断点恢复，或导入时界面冻结。
- 组卷只是 AI 文本输出，没有结构化编辑器、持久化和规则校验。
- 原题/改编题/AI 题没有来源谱系和教师确认。
- 只有备份校验，没有恢复实现和恢复演练。
- 需要用户安装 Node、Python 或手工配置开发环境。
- 关键能力只有后端/IPC，没有前端入口或真实 Electron E2E。
- 原始学生图片或身份信息会默认上传到第三方模型。
- 升级、迁移或卸载可能静默破坏教师数据。
